引言 ​

本文档定义 Chrome 扩展端（Manifest V3，src/）与独立本地 Agent 端（Node.js，agent/src/server.js）之间的内部通信协议。版本以仓库当前双端同步的 2.3.1 为准。

Agent 端提供 HTTP 路由与 WebSocket 服务，暴露文件读写、命令执行、MCP 工具调用、Skill 管理、RAG 知识库、长期记忆、审计日志等能力；扩展端通过 src/background/local-agent-client.js 统一封装配对、认证、HTTP 请求、WebSocket 连接和可达性缓存。

重要运行时约束：

  • Agent 端源码修改后必须重启进程，新接口才生效。
  • 扩展端 Service Worker 存在空闲被终止的生命周期约束，需配合心跳与健康检查保活。
  • 所有需要写操作或敏感能力的接口均要求 Bearer Token 认证，仅健康检查和配对接口可免认证访问。

核心通信契约总览 ​

扩展端与 Agent 端的通信契约围绕三类通道展开：

通道用途关键端点或路径认证方式
HTTP JSON文件、命令、MCP、Skill、RAG、配置、日志、回收站、Agent 管理/api/*多数接口要求 Authorization: Bearer <token>
WebSocket命令执行实时输出、半开连接心跳检测/ws/exec/<execId>?token=<token>URL query token 或 Authorization Header
健康与配对插件发现、Agent 在线状态、一次性配对码/api/status、/api/pair、/api/heartbeat部分免认证，部分需 Bearer Token

Agent 端统一响应结构为 { success, ... }，失败时附带 error；扩展端在 HTTP 层附加 httpStatus，便于区分“Agent 离线”“网络错误”“业务拒绝”。

HTTP 客户端封装与认证 ​

多代理配置与活跃代理 ​

扩展端维护 pairedAgents 数组和 activeAgentId，支持多个已配对 Agent，并通过 getAgentConfig() 获取当前活跃代理的 url、token、agentId。配对成功后，Token 会经过加密存储，读取时再解密。

认证流程 ​

  1. 扩展端调用 /api/pair，携带 code 和 extensionId。
  2. Agent 端校验配对码并返回 token。
  3. 后续所有受保护接口通过 Authorization: Bearer <token> 发送。
  4. Agent 端通过 verifyToken(token) 校验扩展 ID，未认证返回 401，无效 Token 返回 403。

WebSocket 认证 ​

命令执行的 WebSocket 连接优先使用 Authorization Header；由于浏览器原生 new WebSocket() 不支持自定义 Header，扩展端回退到 URL query 参数 ?token=。Agent 端对 WebSocket 同样执行 verifyToken，失败直接关闭连接。

请求、重试与错误处理 ​

基础请求模型 ​

agentRequest(path, body, method, timeoutMs) 是扩展端统一 HTTP 封装：

  • 自动注入 Authorization 和 Accept-Language。
  • GET/HEAD 不携带 body。
  • 超时使用 AbortController，默认 60 秒，上传和下载有更长超时。
  • 成功响应附加 httpStatus，用于区分业务失败和网络失败。
  • 捕获 AbortError 返回“请求超时”，其他异常返回“Agent 请求失败”。

可达性缓存与快速失败 ​

扩展端维护 _agentReachability Map，按 agentId 缓存可达性：

  • null：尚未检测。
  • true：可达。
  • false：不可达。

当已知不可达时，agentRequest 和 agentGet 直接返回“代理服务未连接”，避免阻塞等待超时。

重试机制现状 ​

当前代码中未发现通用指数退避重试实现。重试语义主要由上层调用方决定：

  • 健康检查由 background/index.js 周期性轮询。
  • 长耗时接口（如 RAG ingest、download）通过增大 timeoutMs 容忍延迟。
  • 更新 Agent 的 /api/agent/update 由 Agent 端自身控制 npm 安装和两阶段重启。

会话状态同步 ​

会话状态主要发生在扩展端内部：

  • sessionId 标识一次对话。
  • 子代理使用派生 subSessionId = sessionId + "_sub_" + agentId，隔离流式消息和执行日志。
  • ReAct 循环和工具执行器通过 sessionId 过滤消息，避免主/子任务互相干扰。

Agent 端本身不维护扩展端会话状态；它负责命令执行、文件、MCP、Skill、RAG、记忆等具体能力。

工具调用参数与结果 ​

工具调用链如下：

  1. 侧边栏 chat-manager.js 发起 API 调用。

  3. tool-executor.js 解析 toolCall，提取 name、arguments、id。
  4. 工具调用可能走本地工具或 Agent 端 MCP/Skill/文件系统。
  5. 工具结果通过 tool_call_id 关联到 UI 卡片。

命令执行数据流 ​

命令执行采用 HTTP + WebSocket 组合：

  • HTTP /api/exec 返回 execId 和 wsUrl。
  • 扩展端通过 createExecWebSocket 建立 WebSocket 连接。
  • Agent 端将命令输出推送到对应 execId 的 WebSocket。
  • 支持 wait 模式同步等待结果，也支持异步流式输出。

状态管理与一致性 ​

本地缓存 ​

扩展端维护以下本地状态：

  • pairedAgents：已配对的 Agent 列表，包含 id、name、url、加密后的 token、pairedAt。
  • activeAgentId：当前活跃 Agent ID。
  • _agentReachability：内存中的可达性缓存，按 agentId 区分。
  • skillsCache：Agent Skill 名称集合缓存，60 秒有效，切换代理时清空。

Agent 端维护：

  • 运行中的命令进程。
  • MCP Server 连接状态。
  • Skill 注册表。
  • RAG 可用性检测结果。
  • 回收站条目。
  • 审计日志。

离线支持 ​

当前协议并非完全离线设计：

  • 若 Agent 离线，扩展端可通过可达性缓存快速返回错误。
  • 文件内容、命令输出、MCP/Skill/RAG 结果依赖 Agent 端实时计算。
  • 会话状态保存在扩展端，但工具执行结果通常来自 Agent。

数据一致性 ​

  • 工作目录切换会重新加载配置，并追加到 allowedPaths，只增不减。
  • 删除文件进入回收站，支持恢复和定期清理。
  • Skill 目录变更触发自动重载，无需手动 reload。
  • MCP Server 禁用时会先断开连接，确保工具可用状态一致。

性能优化策略 ​

请求合并 ​

  • ReAct 循环中对连续可并行工具进行分组并发执行，非并行工具单独按序执行。
  • Agent Skill Prompt 获取支持并发 Promise.all，并过滤掉 Workflow 技能减少无效请求。
  • 配对成功后并行拉取 /api/status 和 /api/status/detail 生成 Agent 名称。

连接池管理 ​

  • 扩展端未实现 HTTP 连接池，依赖浏览器底层连接复用。
  • Agent 端使用 Node.js 原生 http 模块和 ws WebSocketServer。
  • WebSocket 连接按 execId 管理，每个命令一个连接。
  • Agent 端维护活跃 socket 集合，优雅关闭时强制销毁。

资源清理 ​

  • Agent 端 shutdown 流程终止运行进程、关闭 MCP 连接、断开 WebSocket、销毁 HTTP socket、清理 PID 文件和回收站定时任务。
  • 命令执行支持 stop 和 detach，前者停止进程，后者显式豁免超时。
  • Skill 目录 watcher 防抖 800ms，避免频繁 reload。

大文件传输优化 ​

  • 普通上传使用 multipart/form-data，限制 200MB。
  • 流式上传 /api/fs/upload-stream 直接接收二进制，避免 base64 膨胀。
  • 下载支持 base64 返回和流式下载两种模式，目录自动打包为 zip。

使用示例 ​

初始化配置 ​

  1. 在设置中配置 Agent 地址。
  2. 调用 pairWithAgent(agentUrl, pairCode) 完成配对。
  3. 成功后 activeAgentId 指向新 Agent，后续 API 自动携带 Token。

推荐调用位置：

  • 设置页或选项页中触发配对。
  • 首次启动时检测是否有已配对 Agent。

异常处理 ​

建议统一处理以下情况：

  • success === false：读取 error 字段。
  • httpStatus === 401：提示重新配对。
  • httpStatus === 403：权限不足或路径不允许。
  • httpStatus === 404：文件不存在。
  • httpStatus === 503：RAG 功能不可用。
  • AbortError：请求超时，建议提示用户延长超时或检查 Agent 是否在线。

调试工具 ​

  • 使用 getAgentStatus() 和 getAgentDetail() 查看 Agent 版本、平台、工作目录、资源使用情况。
  • 使用 queryAuditLogs() 查询最近 7 天的审计日志，支持按分类筛选。

WebSocket 调试要点 ​

  • 确认 wsUrl 来自 /api/exec 响应。
  • 确认 URL 中包含 token。
  • 注意浏览器 WebSocket 不支持自定义 Header，必须使用 query token。
  • Agent 端每 30 秒 ping 一次，两次 pong 未收到则判定连接死亡。

结论 ​

本内部通信协议以 HTTP JSON 为主、WebSocket 为辅，覆盖文件、命令、MCP、Skill、RAG、记忆、日志等核心能力。扩展端通过统一的 local-agent-client.js 封装认证、请求、可达性缓存和错误处理；Agent 端通过 server.js 提供安全可控的路由、权限校验和资源管理。

实际使用中应重点关注：

  • 配对与 Token 生命周期。
  • 路径与命令的安全校验。
  • 长耗时接口的超时配置。
  • WebSocket 连接的建立与心跳。
  • Agent 源码修改后必须重启进程。
  • Service Worker 生命周期导致的连接中断。
