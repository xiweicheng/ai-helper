引言 ​

本项目是一个面向 Chromium 内核浏览器的开源 AI 助手扩展，同时包含一个可选的本地 Node.js Agent 服务。其核心目标是让大语言模型不仅能"聊天"，还能真正操作网页、读写本地文件、执行命令、管理长期记忆与知识库，并通过 MCP 协议和技能系统扩展能力。

从仓库根目录看，项目采用双进程架构：

维度Chrome 扩展端本地 Agent 端
入口manifest.json 声明 Service Worker，实际入口为 src/background/index.jsagent/src/server.js，CLI 入口为 agent/bin/agent.js
包名ai-helperai-helper-agent
版本2.4.0（仓库当前）2.4.0（仓库当前）
通信方式chrome.runtime.sendMessage、chrome.sidePanel、chrome.tabs.sendMessageHTTP REST + WebSocket，默认监听本机地址
主要职责UI、ReAct 推理循环、工具调度、上下文压缩、会话持久化、通知、定时任务文件读写、命令执行、MCP 工具、技能系统、长期记忆、RAG 知识库、安全沙箱

作者提示中强调：安装应以 GitHub Releases 自动构建产物为唯一官方渠道；扩展端与 Agent 端版本号应保持同步；Agent 源码修改后必须重启进程新接口才生效；MV3 Service Worker 存在空闲被终止的生命周期约束；主题使用 CSS Token 体系；i18n 覆盖扩展端 _locales/ 与 agent 端 agent/src/locales；测试体系分两套且不可混跑。

这些约束将直接决定 RepoWiki 文档站点的信息分层、导航结构和读者预期。

详细组件分析 ​

Service Worker 入口与侧边栏生命周期 ​

src/background/index.js 是扩展后台的核心入口，承担的职责远不止消息路由：

  1. 初始化国际化。
  2. 重建定时任务闹钟。
  3. 注册自动续跑闹钟处理器，用于 Service Worker 被系统回收后恢复长任务。
  4. 清理过期的 ReAct checkpoint，并做数据库自检。
  5. 维护 side panel 保活端口，防止 API 调用期间 SW 被判定空闲。
  6. 处理脱离窗口状态。
  7. 管理侧边栏作用域模式：全局模式与标签页绑定模式。
  8. 管理 AI Helper 标签分组。
  9. 处理插件图标点击、快捷键切换侧边栏。
  10. 维护活跃 tab 镜像、焦点状态、面板打开状态。
  11. 处理通知可见性判断。

特别需要注意的是，代码中对 chrome.* API 大量使用可选链保护，以应对 SW 终止瞬间 API 对象可能已被剥离的情况。这是 MV3 Service Worker 生命周期硬约束的直接体现。

性能与运行时约束 ​

Service Worker 生命周期约束 ​

Background Service Worker 可能被 Chrome 在空闲时终止，因此：

  • 长任务需要通过保活端口维持连接。
  • 定时任务和 ReAct checkpoint 需要持久化，以便 SW 重启后恢复。
  • 自动续跑逻辑会在闹钟唤醒 SW 后扫描残留 checkpoint。
  • 所有 chrome API 访问建议使用可选链，避免 SW 终止瞬间抛错。

Agent 进程重启约束 ​

Agent 端支持 /api/agent/restart、/api/agent/update 和 /api/shutdown，但这些操作有防重入和频率限制。更重要的是：Agent 源码修改后必须重启进程，新接口才会生效。这是因为 Node.js 进程已经加载了旧模块，不会热重载。

文件与命令安全 ​

Agent 端对路径和命令做了安全检查，包括：

  • 路径白名单与 realpath 规范化。
  • 命令分级策略。
  • 文件大小限制。
  • 文件回收站。
  • 进程树清理。

主题与 i18n ​

主题使用 CSS Token 体系，支持亮色、暗色、跟随系统三态；暗黑模式经过专项审计。i18n 覆盖两层：扩展端 _locales/ 与 agent 端 agent/src/locales。文档示例应避免缓存写法，确保 UI 名称在渲染时动态查询 i18n。

VitePress 构建约束 ​

更新 VitePress 文档站构建约束已完整实现。

文档站构建有以下约束：

  • Node.js 版本要求 ≥22（ESM 脚本）
  • 构建产物提交到 docs/wiki/ 目录
  • 使用 Pagefind 生成离线搜索索引
  • Mermaid 图表需要在 VitePress 主题中初始化
  • 转换函数必须是纯函数，无文件系统副作用
  • 构建过程包含 6 项硬校验确保质量
  • 最少需要100篇 repowiki 源文档

文档站点导航约束 ​

结论 ​

这个项目不是一个简单的聊天侧边栏，而是一个围绕"浏览器自动化 + 本地代理能力"构建的 AI 助手平台。它的价值不仅在于能调用 LLM，更在于能把 LLM 的输出落到真实网页、真实文件系统、真实终端和本地知识库中。

对于 RepoWiki 文档站点来说，最重要的原则是：

  1. 不要重复 README：README 面向用户快速上手，RepoWiki 面向开发者和技术读者深入理解。
  2. 区分扩展端与 Agent 端：两者是独立进程，有独立生命周期、独立依赖、独立测试。
  3. 突出运行时约束：MV3 Service Worker、Agent 进程重启、CORS、配对认证、安全沙箱都是容易踩坑的地方。
  4. 以架构图和流程图为主：复杂系统更适合用 Mermaid 图表达，而不是纯文字。
  5. 保持版本一致性：文档应以仓库当前版本为准，并注明扩展端与 Agent 端版本应同步。
  6. 引导到权威文档：已有英文完整文档和中文文档链接，RepoWiki 应补充结构化的技术参考，而不是复制现有文档。

附录：VitePress 迁移实施方案 ​

目标 ​

VitePress 迁移方案的目标是将现有的 RepoWiki 文档（132 篇中文 Markdown）构建为 VitePress + Pagefind 静态文档站，产物提交到 docs/wiki/，经现有 GitHub Pages（main/docs）发布到 https://xiweicheng.github.io/ai-helper/wiki/。

技术栈：VitePress（devDep）、Pagefind（devDep，用其 pagefind-ui 现成搜索组件）、mermaid（devDep，ESM 包）、Node ≥22 ESM 脚本、Vitest（test/unit）。

架构：一条本地命令 npm run build:docsite 串联四步：① 纯函数转换 repowiki MD（file:// → GitHub blob 链接、目录树 → 侧边栏、文件名空格→-、注入 frontmatter）到 gitignore 暂存目录 .docsite-src/；② 生成 VitePress 配置与主题（mermaid fence、Pagefind 搜索覆盖层）；③ vitepress build 输出到 docs/wiki/；④ pagefind 生成索引并跑 6 项硬校验。部署完全复用现有 push 链路。
