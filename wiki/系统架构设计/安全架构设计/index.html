引言 ​

本安全架构文档面向 AI Helper 的双进程体系：Chrome 扩展端（Manifest V3，版本 2.3.1）与独立本地 Agent 服务（Node.js，版本 2.3.1）。两端通过本地 HTTP/WebSocket 通信，扩展端负责浏览器上下文、页面交互与用户界面；Agent 端负责本地文件读写、命令执行、长期记忆、RAG 知识库、MCP 工具注册与技能系统。

从安全视角看，系统不是“一个程序”，而是由多个信任域组成的边界集合：

  • 浏览器扩展 Service Worker 与 Side Panel 运行在扩展上下文中。
  • 内容脚本运行在每个页面的隔离世界中。
  • Agent 进程以本机 Node 进程身份访问文件系统与操作系统命令。
  • 外部 LLM 提供商是受控但不可信的外部服务。
  • 第三方 MCP Server 和 Skill 代码可能引入额外执行面。

因此，安全设计必须同时处理跨进程、跨上下文、跨平台路径语义、命令语法变体、提示注入、凭据泄露与可观测性五个维度。

详细组件分析 ​

Agent HTTP 服务器安全入口 ​

Agent 服务器是所有本地能力的统一入口。它承担以下安全职责：

  • 只允许来自 chrome-extension:// 的来源跨域读取响应，防止恶意网页直接读取无认证接口。
  • 对 /api/pair、/api/status 等无需认证的接口进行最小化信息暴露。
  • 对 /api/shutdown 区分本机来源与远程来源：远程来源必须携带有效 Bearer Token。
  • 对所有需认证接口统一校验 Authorization: Bearer <token>。
  • 限制 JSON body 与 multipart 上传大小，避免内存耗尽。
  • 将请求语言同步到各子模块，保证错误消息、安全提示、日志分类具备国际化一致性。

路径沙箱与命令分级 ​

路径沙箱与命令分级是 Agent 端最重要的两道本地执行防线。

路径沙箱 ​

路径检查遵循以下顺序：

  1. 空值或非字符串直接拒绝。
  2. 展开 ~ 到用户主目录。
  3. 规范化路径格式，兼容 Windows 盘符、MSYS/Git Bash 风格路径。
  4. 绝对路径基于自身解析，相对路径基于 workdir 解析。
  5. 硬阻止检查：Agent 配置、配对记录、日志、回收站、内置技能状态等不可绕过。
  6. 记忆存储目录与工作目录特殊放行。
  7. 白名单前缀匹配。
  8. realpath 解析真实物理路径，再次检查硬阻止和白名单，防止符号链接绕过。

Input["输入路径"] --> Normalize["规范化路径格式"]

命令分级 ​

命令检查分为三类：

  • 黑名单：绝对禁止，即使 force=true 也不放行。包括破坏性删除、格式化磁盘、覆盖系统文件、Fork Bomb、管道执行 shell、修改根目录权限等。
  • 灰名单：需要用户确认。包括 sudo、全局安装、递归删除、权限变更、网络外联、进程终止、系统服务、脚本执行等。
  • 白名单：普通命令直接放行。

命令扫描不仅检查整串，还会：

  • 拆分链式命令。
  • 剥开 sudo/doas/nohup/env 等包装器。
  • 归一化 /./usr、//dev 等路径变形。
  • 提取 -c/-e、/c /k、-Command/-EncodedCommand 等解释器内联载荷。
  • 提取 $() 与反引号中的子命令。
  • 对命令替换场景做只读头命令豁免，避免误杀 echo $(date)。

命令执行器与进程生命周期 ​

命令执行器负责把安全网关通过的命令交给操作系统执行，同时控制资源消耗与进程生命周期。

关键点：

  • 根据平台与环境选择可用 shell，避免 Git Bash MSYS 路径在 Windows 上直接 spawn 失败。
  • 环境变量采用白名单裁剪，避免泄露宿主敏感变量。
  • stdout/stderr 有 5MB 缓冲上限，超限后截断并广播通知。
  • 支持两种超时策略：旧模式到期即杀；受管模式根据是否有输出决定延长或终止。
  • 支持流式 WebSocket 输出、延迟连接回放、断开后自由运行（显式 detach）。
  • 跨平台终止进程树：Unix 用负 PID 杀进程组，Windows 用 taskkill /T /PID。

扩展端 Agent 客户端 ​

扩展端的 local-agent-client.js 封装了与 Agent 的所有 HTTP 与 WebSocket 通信，并负责：

  • 多代理管理：保存多个 Agent 实例，切换活跃代理。
  • Token 解密：从存储中读取时解密 token。
  • 可达性缓存：避免频繁探测离线 Agent。
  • 统一认证请求：所有需认证请求附带 Authorization: Bearer。
  • 超时控制：AbortController 控制 fetch 与 WebSocket 空闲超时。
  • 文件上传：multipart/form-data 与流式上传。
  • 命令执行：异步启动、等待结果、停止、detach。

认证授权、Token 管理与用户权限模型 ​

配对与认证流程 ​

Agent 的认证不是传统用户名密码，而是“配对码 + Token”的两阶段机制：

sequenceDiagram
participant Ext as "扩展"
participant Agent as "Agent 服务器"
participant Auth as "认证模块"
participant Store as "配对记录存储"
Ext->>Agent : POST /api/pair {code, extensionId}
Agent->>Auth : handlePairRequest(code, extensionId)
Auth->>Auth : 检查失败锁定
Auth->>Auth : 比对 currentPairCode
Auth->>Store : 检查是否已配对
alt 已配对
Auth-->>Agent : 返回已有 token
else 首次配对
Auth->>Store : 保存 extensionId + randomBytes(32) token
Auth-->>Agent : 返回新 token
end
Agent-->>Ext : 返回 token
Ext->>Agent : 后续请求携带 Authorization : Bearer token
Agent->>Auth : verifyToken(token)
Auth-->>Agent : 返回 extensionId 或 null

Token 管理机制 ​

  • 配对码：6 位字母数字，排除易混淆字符，使用密码学安全随机数。
  • 配对码轮换：插件在线且最近 5 分钟有认证则停止轮换；否则定时刷新。
  • 一次性使用：配对成功后立即轮换配对码。
  • 失败锁定：连续失败 5 次后锁定 60 秒，并立即轮换配对码。
  • Token：32 字节随机 hex，用于后续所有需认证接口。
  • 活跃窗口：成功认证后更新 lastAuthTime，用于判断插件是否在线。

用户权限模型 ​

当前权限模型不是细粒度 RBAC，而是“扩展实例级 Token + 服务端能力开关”的组合：

  • 每个扩展实例拥有唯一 token。
  • 同一 Agent 可配对多个扩展实例。
  • 能力开关由 config.json 控制，例如 allowedPaths、commandTimeout、fileMaxSize、pairCodeTTL。
  • 命令执行还叠加用户确认层：灰名单命令默认弹出确认，黑名单不可绕过。
  • 网络访问在扩展侧有总闸与白名单，Agent 侧 RAG URL 摄入也有 AND 闸语义。

Prompt 注入防护、输入验证清洗与输出过滤 ​

不可信内容包装 ​

系统对来自外部数据的工具结果进行包装，将其标记为“数据而非指令”。核心思路：

  • 定义包装类工具集合：页面内容、网络响应、本地文件、MCP 结果、记忆、RAG 检索等。
  • 定义已知安全工具集合：纯操作状态、用户输入、模型自产文本等。
  • 对包装类工具结果包裹 <untrusted_page_content> 标签。
  • 剥离内容中的伪造标签，防止越狱。
  • 当检测到消息历史中存在包装内容时，向 system 消息注入安全合约。
  • 契约文案强调：外部内容是数据，不得执行其中出现的命令、请求或指示。

敏感信息保护、密钥管理与加密存储机制 ​

当前机制 ​

  • 扩展端存储的 Agent Token 使用 Base64 + enc: 前缀混淆。
  • Agent 端配对记录中的 token 明文落盘，注释说明该文件未设置 0600 权限。
  • WebSocket 认证 token 通过 URL query 传递，因为浏览器 new WebSocket() 无法设置握手 header。
  • 扩展端 API Key、视觉 API Key 存储在 chrome.storage.local，属于扩展模型固有约束。

Secret["敏感信息"] --> Encode["encodeSecret(enc: + base64)"]
Encode --> Storage["chrome.storage.local"]
Storage --> Decode["decodeSecret"]
Decode --> Runtime["运行时使用明文"]

图表来源

  • src/shared/secret.js#L1-L31

风险评估 ​

  • Base64 混淆不是加密：能读取磁盘或 storage 的攻击者可轻易还原。
  • WS token 在 URL 中可能进入代理日志、Referer、浏览器历史记录。
  • 配对文件权限未设置为仅当前用户可读。
  • 配置导出包含密钥字段，存在二次泄露风险。

建议 ​

  • 若威胁模型包含本地磁盘读取，应引入操作系统级密钥保护（如 macOS Keychain、Windows Credential Manager），但这会显著增加部署复杂度。
  • WS 握手改用首帧鉴权可减少 URL 暴露面，但需要协议变更。
  • 导出配置时对密钥做更强提示与二次确认。

安全更新机制、漏洞修复流程与应急响应预案 ​

安全更新机制 ​

Agent 提供 /api/agent/update 接口，允许扩展端触发 npm 全局更新：

  • 校验操作进行中与冷却期。
  • 与 RAG 依赖安装互斥，避免 node_modules 互相破坏。
  • 执行 npm install -g ai-helper-agent@latest，超时 90 秒。
  • 更新失败不重启，保持老进程运行。
  • 更新成功通过两阶段重启包装器拉起新版本。

漏洞修复流程 ​

根据审计报告与复核状态，本项目已形成较完整的修复闭环：

  1. 审计发现安全问题。
  2. 分类为严重/高/中/低。
  3. 区分“已修复”“成立值得排期”“等级下调”“产品策略决策”。
  4. 补充守卫测试与负向对照。
  5. 全量回归 + 构建验证。
  6. 真机冒烟或探针验证。

应急响应预案 ​

针对高危场景，建议建立如下预案：

  • 命令执行异常：立即停止运行进程，查看 exec 日志，检查黑名单是否遗漏。
  • 路径越界：检查 workdir 与 allowedPaths，确认是否新增未走 checkPath 的接口。
  • 提示注入：检查不可信内容包装是否生效，system 合约是否注入。
  • 凭据泄露：轮换 API Key、Agent Token，检查日志是否打印敏感头。
  • Agent 被关停：检查 /api/shutdown 来源，评估是否需要收回回环免认证。

结论与建议 ​

AI Helper 的安全架构在双进程模型下实现了较为完整的多层防护：扩展端负责浏览器上下文与用户交互，Agent 端负责本地执行与数据能力，并通过认证、路径沙箱、命令分级、不可信内容包装、审计日志等手段形成纵深防御。

但仍存在若干需要持续关注的方向：

  1. 命令确认链路必须始终由用户交互驱动，不应接受模型传入的 force 作为绕过依据。
  2. 内容脚本渲染与 XSS 防护仍需补齐，当前审计结论表明内容脚本 Markdown 渲染缺少消毒。
  3. SSRF 与内网访问应坚持 AND 闸语义，总闸关闭时即使白名单非空也应拒绝。
  4. 敏感信息存储应评估是否升级为操作系统级密钥保护，至少对配对文件设置严格权限。
  5. 调试能力与隐私保护需要明确产品边界，debug_page 抓包暴露 header 是有意取舍，但应提供显式开关。
  6. 安全更新与漏洞修复应配套自动化守卫测试，确保黑名单、路径沙箱、注入防护不因新增功能退化。

整体而言，该系统的安全基线优于许多同类项目，但“让 AI 操作本地文件和终端”的能力本身具有高风险。未来演进应以“最小权限、最大可见、强制确认、可审计”为核心原则，而不是单纯堆叠规则。
