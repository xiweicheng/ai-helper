# 语音输入：句级即时精修（消除草稿与定稿的体验断层）设计文档

日期：2026-10-30
状态：待 review（brainstorming 三节已与用户逐节确认）

## 背景与目标

当前语音输入是**两段式**：说话时用 `Streaming Zipformer 中英双语（int8）` 出逐字草稿，松手后整段交给 `SenseVoice 中英韩日粤（int8）` 重转。用户反馈：

> 开始流式输出后，实时输出的草稿内容不准；我停顿以后，又突然用另一个模型去识别。从模型到最终定版的转文字，中间差别太大，导致体验很差。用户在说话过程中看到的草稿，牛头不对马嘴。

目标（用户已明确选择「必须保留边说边出字，但要准」）：

1. 说话过程中看到的文字要**准**，不能是"牛头不对马嘴"的草稿；
2. 松手后的修正**可以保留**（用户认可其他语音输入法"结束后整体修正"的做法），但不能是"整段突然被推翻"；
3. 不降低最终文本的质量上限。

## 现状链路

```
PCM 帧 ──┬─→ zipformer stream ─→ pumpPartial() 每 150ms ─→ {type:'partial'}
         │                    └─→ isEndpoint() ─→ handleEndpoint() ─→ {type:'endpoint'}
         └─→ session.chunks.push()（整段累积，供 stop 用）

stop ─→ finalize() ─→ transcribe(整段 PCM) ─→ {type:'final'}
```

前端 `voice-input.js`：`partial` / `endpoint` 都走 `applyDraft(text)`，**整段替换**草稿区间 `[start, start+len)`；`final` 走 `finalizeText()`，再做一次整段替换。

### 根因拆解（两个独立问题）

**问题 A：草稿质量差 —— 是两个不同模型的产物差异**

| | 流式草稿 | 定稿 |
|---|---|---|
| 模型 | Streaming Zipformer bilingual zh-en（2023-02，int8） | SenseVoice zh/en/ja/ko/yue（int8） |
| 架构 | transducer，词级增量 | 非自回归整段 |
| 标点 | 无 | 有 |
| 数字规整（ITN） | 无 | 有 |

差的是三件事叠加：错字率 + 标点 + 数字/单位规整。且 zipformer 是 2023 年初的双语小模型，中英混说基本会崩。

**问题 B：落差一次性爆发 —— 定稿整段覆盖**

`finalize()` 把整段 WAV 交给 SenseVoice，回来的 `final` 由 `finalizeText()` → `applyDraft(finalText)` **一次性重写整个草稿区间**。于是"全段 × 三种差异"同时发生。

## 关键事实核查（含实测）

### 问一：松手后的「整段重转」到底是不是整段推理？

答：**取决于 VAD 是否启用，而当前默认禁用。**

`agent/src/asr/engine.js:293` 有一道硬开关：

```js
export function getVad(model, opts = {}) {
  if (!model) return null;
  if (process.env.AI_HELPER_ASR_VAD !== '1') return null;   // 默认关闭
```

注释说明了原因：sherpa-onnx-node 2.0.1 在 `vad.front()` 首次取段时**直接 SIGSEGV**（EXC_BAD_ACCESS），原生层崩溃 JS 的 try/catch 拦不住，整个代理进程当场退出，且无日志栈可追。全仓库（含安装脚本）**没有任何地方设置该环境变量**。

因此 `splitByVad` 走 `fixedChunks()`：**按 30 秒固定切块**。对绝大多数语音输入（< 30s），**那就是一次性整段推理，SenseVoice 确实看到了完整上下文**。

> 早期版本的本设计曾误以为 VAD 默认启用，据此推出「整段 = 分段解码、逐句不损失质量」。该推断**作废**，以下一律以实测为准。

### 问二：整段 vs 逐句，哪个更准？—— 实测

方法：`say` 合成 3 组语音（多句口述 / 单句长语音 / 中英混说+数字），用项目自己的 `parseWav` + `getOfflineRecognizer` 跑三种喂法。探针：`test-results-probes/_asr-segment-quality.mjs`。

**纯字词 CER（去标点）：**

| 场景 | 整段 | 逐句 | 8s 硬切 |
|---|---|---|---|
| A 多句口述 17.8s | 0.0% | 1.4% | 0.0% |
| B 长句 13.1s | 0.0% | 0.0% | 1.7% |
| C 中英+数字 11.9s | 11.1% | 11.1% | 14.8% |
| **平均** | **3.7%** | **4.2%** | 5.5% |

字词差距 0.5pp，且**全部来自一处**：A 场景逐句把「它」写成「他」。B、C 两场景逐句与整段**完全一致**。

**含标点 CER + 句末标点数：**

| 场景 | 参考句号 | 整段 | 逐句 | 8s 硬切 |
|---|---|---|---|---|
| A | 4 | 2.5% / **2 个** | **1.3% / 4 个** | 7.6% / 4 个 |
| B | 1 | 3.4% / 1 | 3.4% / 1 | 6.8% / 2 |
| C | 1 | 13.8% / 1 | 13.8% / 1 | 19.0% / 2 |
| **平均** | | **6.6%** | **6.2%** | 11.1% |

耗时持平（整段 714/556/736ms vs 逐句 746/519/713ms）。

**四条结论：**

1. **字词**：整段略好（0.5pp，仅一处同音字），逐句几乎不输。
2. **断句**：逐句明显更好。整段解码会把相邻句用逗号串起来（4 句 → 只输出 2 个句号），逐句 4 个全对 —— 因为它天然知道「这句说完了」。
3. **硬切必须禁用**：切在词中间会产生垃圾（`牛。头不对马嘴`、`松手之后。后仍然`、`230。9兆`）。这否掉了「8 秒强制切句」这个兜底信号。
4. **耗时持平**：逐句没有变慢。

**局限（必须写明）**：TTS 合成音没有人声噪声、口音与气息，**低估了整段的上下文优势**。方向可信，幅度偏乐观。后续拿到真实录音应按同一方法复测。

## 最终文本策略：字词取整段补正，断句取逐句

实测证明「整段结果无条件覆盖」是错的 —— 它会把已经正确的句号改回逗号，而这正是用户会感知到的「突然变」。

结论：**以逐句精修拼接为最终文本的骨架（词与句读），整段重转只用来补正字词，永不动标点。**具体算法见「agent 侧设计 · 5. final」。

这既保留了用户认可的「结束后整体修正」，又保证修正只改字、不改句读。

## 方案取舍

| 方案 | 结论 | 理由 |
|---|---|---|
| **1. 句级即时精修 + 松手整段字词补正**（采纳） | ✅ | 同时解决「不准」与「突然变」；实测证明逐句在断句上反而更好 |
| 2. 换流式模型让草稿与定稿同源 | ❌ | SenseVoice 无真正流式实现；sherpa-onnx 高质量流式模型可选面窄；换完仍可能不达标 |
| 3. 只做定稿 diff 对齐 + 视觉分档 | ❌ | 纯前端成本低，但完全不解决「说话中看到的是错的」 |
| 4. 诚实模式（不出逐字草稿） | ⚠️ 降级档保留 | 零落差，但丢掉核心卖点；作为「精确」档与低配降级落点 |
| 5. 松手整段结果无条件覆盖 | ❌ 实测否决 | 会把已经正确的句号改回逗号（4 句 → 2 句），这正是用户感知到的「突然变」 |
| 6. 8 秒强制切句做兜底 | ❌ 实测否决 | 切在词中间会产生垃圾（`牛。头不对马嘴`、`230。9兆`） |
| 7. silero VAD 做切句信号 | ❌ 不可用 | 当前版本 `vad.front()` 必 SIGSEGV，整个代理进程退出 |

**关键决策**：说话中逐句精修、松手整段字词补正、断句始终以逐句为准。用户既要即时感，也要最终质量，且要求「修正」存在但不粗暴。

## 设计总览

```
PCM 帧 ──┬─→ zipformer ─→ partial（150ms 节流）
         ├─→ isEndpoint() ───────────┐
         └─→ RMS 静音 ≥300ms ────────┼─ 切句（禁止无脑硬切）
                                     ↓
                         segFrames 按帧存储 → 精修队列（可中止）
                                     ↓
                              {type:'sentence', id, refined}

stop ─→ 中止待精修 → transcribe(整段) ─→ {type:'final', text, segments}
                                     ↓
              前端：字词取整段补正、断句保逐句 → 只改字不改句读
```

## agent 侧设计

### 1. 切句信号（两取一 + 一个长句兜底，且禁止硬切）

| 信号 | 说明 |
|---|---|
| `isEndpoint()` | 主信号，沿用 zipformer，零成本 |
| **RMS 连续静音 ≥ 300ms** | 次信号。不用 silero VAD（必崩），改用纯 JS 算每帧 RMS（帧长 100ms，阈值 0.006，连续 3 帧低于阈值即切） |
| 单句 ≥ 12s | 回溯最近 2s 内 **RMS 最低的一帧**作为切点（大概率落在词间停顿）；找不到合适点就不切，留到 stop 整段处理 |

**为什么不能用固定时长硬切**：实测场景 A 的 8s 硬切产生 `牛。头不对马嘴`、`松手之后。后仍然`、`230。9兆` —— 切在词中间会同时造成漏字与重复，CER 从 3.7% 升到 5.5%。宁可等，不可乱切。

**超长句不精修的取舍**：若用户连续 15 秒不停顿且无合适切点，该句放弃逐句精修，留到 stop 时整段处理。用户看到的是「这段时间没出字」，而不是一堆错字。

### 2. 句样本缓冲：按帧存，不按字节偏移切片

`session.chunks` 是 `Float32Array[]`，无样本偏移索引。但切点必须能落在帧边界（包括回溯）上，因此不能只做简单的「切完就清空」，要按帧存：

```js
session.chunks.push(samples);                    // 整段，供 final
session.segFrames.push({ samples, rms: rmsOf(samples) });  // 当前句，按帧
```

切句时：

```js
const cut = chooseCutIndex(session.segFrames);   // 帧索引
const head = session.segFrames.slice(0, cut);
const tail = session.segFrames.slice(cut);
session.segFrames = tail;                        // 尾巴留给下一句
const segSamples = concatChunks(head.map((f) => f.samples));
```

### 3. 精修任务的队列约束（关键）

`runOfflineTask` 是**全局串行 FIFO**（`queue = queue.then(...)`）。若精修直接入队，松手时那条整段定稿会排在所有待精修句子后面 —— **松手反而变慢**。

解法（不改队列结构）：

- 每个精修任务闭包捕获 `session`，执行体**第一行**检查 `session.refineAborted`，为真则立即 `return null`（毫秒级空转）；
- `stop` 时先置 `session.refineAborted = true`，再发 `final` 任务 → 排队中的精修瞬间空转完，final 立即开始；
- 精修结果回来时若 `session.released` 已为真，直接丢弃（不发帧）。

### 4. 背压与降级

| 条件 | 行为 |
|---|---|
| **待执行**（pending，尚未被 worker 取走）的精修任务 > 3 | 丢弃最旧的那条（该句保持草稿，不影响正确性） |
| RSS > `RSS_LIMIT_BYTES` | 关闭逐句精修，退回今天的行为 |
| 连续 3 次精修耗时 > 句长 × 1.5 | 判定机器跟不上，关闭逐句精修 |
| 句长 < 0.6s | 跳过精修（SenseVoice 对超短音频质量会掉） |

降级后前端收到 `{type:'refine', enabled:false}` 一次，录音条提示一次，不反复骚扰。

### 5. final：整段重转 + 字词补正

整段重转保留（提供上下文优势），但结果**不直接覆盖**逐句文本。`transcribe()` 需同时返回分段文本与每段时长，供前端做按句对齐：

```js
return { text: tidyJoin(texts), segments: segments.length, texts, peak };
```

`final` 事件新增 `segments: string[]`。`text` 字段保留（向后兼容 + fallback 路径）。

**前端缝合算法**（纯函数 `mergeRefined(draftSentences, finalText)`，可单测）：

1. 去标点后比较 `draft` 与 `finalText`
2. 长度相同且差异 ≤ 2 字符 → 把差异字符逐个替换进 `draft`，**标点位置完全不动**
3. 差异超阈值 → 逐句结果出了实质问题（漏句/串句），整段接管

阈值取 2 字符的依据：实测两路差最大一次仅为 1 字（它/他）。

## 协议变更

新增两处，其余不变：

| 事件 | 字段 | 说明 |
|---|---|---|
| `sentence`（新，S→C） | `id:number`、`draft:string`、`refined:string\|null` | 同一 id **发两次**：切句时发 `refined:null`（告知前端「这句已结束、id 已分配」），精修完成后发带 `refined` 的第二帧。`id` 从 1 起单调递增 |
| `refine`（新，S→C） | `enabled:boolean`、`reason?` | 会话开始时在 `ready` 帧里带一次；运行中降级时再发一次（`enabled:false`） |
| `final`（改） | 新增 `segments:string[]` | 权威分段文本 |

**为什么 `sentence` 要发两次**：精修是异步的，前端必须先知道「哪段文本对应哪个 id」才能在结果回来时定位替换；只在完成时发一帧，前端就无从知道该句的边界。

`partial` / `endpoint` 保留不动（精修开启时前端只用它们驱动"开放句"，不用它们改写已精修句）。

## 前端设计

### 1. 草稿结构：单区间 → 句表

```js
st.draft = {
  start,                    // 整块草稿在输入框的起点
  items: [                  // 按序
    { id: 1, text: '第一句。', state: 'refined' },  // state: draft | refined | locked
    { id: 2, text: '第二句。', state: 'refined' },
    { id: null, text: '正在说的这', state: 'draft' },  // id=null = 开放句
  ],
}
```

写入输入框 = `items.map(i => i.text).join('')` 整体重写 `[start, start+len)`；`len` 由拼接结果算出，不再手工维护。

**开放句的 id 必须是 `null`，不能是 `0`** —— 服务端的 `id` 从 1 起单调递增，用 `0` 会与真实 id 撞车，导致精修结果错误地替换掉正在说的那句。同一时刻最多一个开放句：新句到达时，旧开放句转为正式 item。

### 2. 用户手改归位（`locateEdit` 纯函数）

1. 求「改动前草稿全文」与「改动后输入框」的公共前缀长 `p`、公共后缀长 `s`
2. 改动区间 = `[p, oldLen - s)`
3. 与改动区间有交集的 item → `state = 'locked'`

| 情况 | 处理 |
|---|---|
| 改在草稿块之前/之后（不碰草稿） | 不锁句；按长度差平移 `start`，草稿内容不动 |
| 大段粘贴/整段删除（跨多句） | 交集涉及的每一句都 lock（"只锁一句"在此无可执行语义） |
| 改的是开放句（正在说的那句） | 锁定它；后续 partial 退回 `appendOnlyDelta` 语义（原样复用，不重写历史教训） |

### 3. 精修 / 校正落地

- `sentence.refined` 到达：id 不存在（已取消）→ 丢弃；`state === 'locked'` → 丢弃；否则替换该句文本并重算 `len`。**句长变化不得影响 `start`**。
- `final` 到达：调 `mergeRefined(items, finalText)`（见 agent 侧 5）。
  - 字词补正：只改字，标点位置不动；**只对 `state !== 'locked'` 的句生效**，lock 句的字也不改（用户已表达意图）。
  - 整段接管（差异超阈值）：逐句结果出了实质问题，**此时 lock 句也一并丢弃**，否则会出现「用户改过的半句 + 整段全文」的重复。
- 录音条提示：有字词补正时显示「已校正 N 处」一次；差异为 0 时静默，不写输入框。

### 4. 光标

句长变化导致整体重写。光标在草稿块**之前**或**内部** → 按相对偏移恢复；在块**之后** → 按长度差平移。否则每来一句精修光标就跳回草稿末尾，用户没法在输入框后半段打字。

### 5. 视觉分档

**不做句内高亮**。输入框是 `<textarea>`，无法给区间上色；句级替换发生在同一位置、通常只差几个字，加高亮反而更扰动视觉。分档信息只进录音条：`正在听…（已定稿 2 句）`、校正时 `正在校正…`。

## 配置

配置页「语音 → 识别节奏」三档，共用同一套基础设施：

| 档位 | 行为 |
|---|---|
| 即时（= 今天） | 只出流式草稿，松手整段定稿 |
| **均衡（默认）** | 句级精修 + 松手整段校正 + 逐句 diff |
| 精确 | 不出逐字草稿，每句结束才出一次准文本 |

这一层不是为增加配置项，**它是自动降级的落点** —— 没有它，"低配机器上怎么办"没有答案。

## 测试计划

### agent 侧（`node --test agent/test/unit/*.test.js`）

- `isEndpoint()` 命中即切句；RMS 连续 3 帧低于 0.006 即切；带 12s 超长句时切点回溯到最近 2s 内 RMS 最低帧
- **禁止硬切**：源码守卫不得出现「按固定样本数直接切」的实现（实测会产生 `牛。头不对马嘴`、`230。9兆`）
- 切句后精修任务携带 `segFrames` 头部样本，尾巴（`slice(cut)`）留给下一句
- 队列 > 3 时丢弃最旧**未开始**的，保留最新
- `stop` 置 `refineAborted` 后，待精修任务空转返回、final 立即执行（**断言执行顺序，不只断言结果**）
- RSS 超阈值 / 自适应降级：关闭精修，`final` 仍出结果
- 句长 < 0.6s 跳过精修
- worker 抛错 → 该句保持草稿、不影响邻句、不发 `sentence` 帧
- 断连 / 取消 → 精修任务不泄漏（`release` 后结果被丢弃）

### 前端（`npx vitest run`）

- `applySentence`：refined 替换 + 长度重算；`locked` 忽略
- `locateEdit`：块外编辑不锁句但平移 `start`；跨多句全部 lock；开放句被改 → lock
- 精修乱序回传（id 2 先于 id 1 到）
- 过期 id 丢弃
- `final` 到达的 `mergeRefined`：字词差异 ≤ 2 字符时只替换字符、句号位置完全不变；差异超阈值时整段接管；lock 句的字不被改
- 光标恢复：块前 / 块内 / 块后三种

### 真机探针（Playwright + 真实 agent）

两个必须防的假通过陷阱：

1. **只断言"输入框有文本"是无效的** —— 草稿态也满足。必须断言某句的**具体字符**等于 SenseVoice 定稿结果。
2. **若切句未生效，整段会被当成一句**，逐句精修悄悄退化成整段。必须断言**句数等于预期值**（如 4 句），且**句号数量正确**（实测：整段解码会把 4 句串成 2 个句号）。

另做变异验证：把"用精修替换"改回"用草稿"，守卫测试必须变红；否则守卫是恒真的。

## 风险与明确不做

- **CPU 竞争**：SenseVoice int8 约 239MB，说话时跑可能抢 CPU 导致录音丢帧 —— 靠队列上限 + 自适应降级兜底，不追求零影响。
- **长句不停顿**：超过 12s 会回溯到最近的静音帧切；若整段找不到合适切点则放弃该句精修、留到 stop 整段处理（用户看到「这段时间没出字」而不是一堆错字）。
- **标点与字词分属两个来源**：断句信逐句（实测更好），字词信整段（实测略好）。两者分歧时的缝合规则见 agent 侧 5。
- **真实录音未验证**：本次实测基于 TTS 合成音，低估了整段的上下文优势。上线后应拿真实口述音频复测 `_asr-segment-quality.mjs`。
- **明确不做**：不更换流式模型；不引入真正流式的高质量模型；不对输入框做区间着色；不做句内 UI 标记；不启用 silero VAD（必崩）。

## 验收标准

1. 说话过程中，每一句精修落地后，输入框中该句文本与 `SenseVoice` 对该段音频的定稿结果**逐字相同**。
2. 松手后，最终文本的**句号数量与位置保持不变**（整段补正不得把句号改回逗号）；字词补正处数 ≤ 2（依据：实测两路最大差异仅 1 字）。超阈值时整段接管，但必须命中实测验证过的「逐句串句」情形。
3. 用户在草稿块外编辑输入框，不影响任何句的精修；用户在某一句话内编辑，**只有那一句**停止精修。
4. 低配机器触发降级后，行为与今天完全一致（松手整段定稿），录音条提示一次。
5. 松手到出最终文本的耗时**不高于**今天（不允许因排队变慢）。验证方式：同一段音频在「即时」档与「均衡」档各跑一次，`stop` → `final` 的时间差不超过 15%。
6. 全量回归通过：`npx vitest run`、`node --test agent/test/unit/*.test.js`、`npx eslint src/ agent/`、`npm run build:silent`。
