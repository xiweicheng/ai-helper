引言 ​

本文件聚焦 AI Helper 的 MCP 工具注册与发现机制。该机制由两部分组成：

  • Agent 端（Node.js）：负责加载 MCP Server 配置、建立连接、拉取工具列表、维护已连接客户端，并暴露 HTTP API。
  • 扩展端（Chrome 扩展 Background）：负责从 Agent 拉取工具定义，将其转换为内部工具模型，注入执行器，并在运行时转发调用。

整体目标是让任意实现 MCP 协议的第三方服务，都能以“零集成代码”的方式成为 AI 助手可调用的工具。

核心组件总览 ​

MCP 客户端类 ​

McpClient 是单个 MCP Server 的生命周期抽象。它负责：

  • 根据配置创建传输层：stdio、SSE、Streamable HTTP、WebSocket。
  • 建立 MCP 连接。
  • 获取服务端版本和能力。
  • 拉取工具列表。
  • 调用工具并标准化返回结果。
  • 断开连接并清理资源。

MCP 注册表 ​

注册表维护一个 Map，键为 serverId，值为 McpClient。它对外暴露：

  • initializeMcpRegistry：启动时连接所有启用 Server。
  • getMcpServersStatus：查询 Server 状态、工具数量、工具详情。
  • getMcpTools：扁平化工具列表，支持按 Server 过滤。
  • callMcpTool：通过 Server ID 和工具名调用远程工具。
  • connectMcpServer / disconnectMcpServer：运行时连接管理。
  • shutdownMcpRegistry：Agent 关闭时统一释放连接。
  • setMcpRegistryLang：同步当前语言。

  • 带 mtime 的内存缓存。
  • 写入互斥锁，避免并发写破坏 JSON。

架构总览：扩展端、Agent 与 MCP Server 的关系 ​

AI Helper 采用双进程架构：

  • 扩展端：Manifest V3 Service Worker，负责 UI、会话、提示词、工具选择和本地执行逻辑。
  • Agent 端：独立 Node.js 进程，提供文件、命令、记忆、RAG、Skill 和 MCP 工具能力。
  • MCP Server：第三方服务，实现 MCP 协议，向外暴露工具。

动态工具注册流程 ​

动态工具注册发生在两个阶段：

  1. Agent 启动阶段：加载配置并连接 MCP Server，拉取工具列表。
  2. 扩展端运行阶段：从 Agent 拉取工具定义，转换为内部工具模型，注册到执行器。

Agent 端工具发现 ​

Agent 启动后，在 HTTP 服务器监听成功后，异步初始化 MCP 注册表。注册表会：

  • 读取 mcp_servers.json。
  • 跳过未启用的 Server。
  • 为每个启用 Server 创建 McpClient。
  • 调用 connect() 建立连接。
  • 通过 listTools 拉取工具。
  • 将成功连接的客户端存入 clients Map。

扩展端工具注入 ​

扩展端 Background 的 loadMcpTools 负责把 Agent 提供的工具映射到内部工具系统：

  • 检查全局 mcpEnabled 开关。
  • 清理之前注册的 MCP 工具。
  • 并行获取工具列表和服务端状态。
  • 过滤掉被禁用的 Server。
  • 生成唯一工具 ID：mcp_{serverId}_{toolName}。
  • 去重防止重复注册。
  • 构造内部工具定义，包含分类、执行位置、参数 Schema。
  • 注册处理器，实际调用走 AgentClient.callMcpTool。
  • 持久化 mcpTools 供 UI 显示。

工具自动发现机制 ​

配置文件解析 ​

MCP 工具自动发现的起点是 ~/.ai-helper-agent/mcp_servers.json。该文件结构由 mcp-config.js 定义，核心字段包括：

字段类型说明
servers数组MCP Server 配置列表
id字符串Server 唯一标识
name字符串显示名称
transport字符串传输方式：stdio、sse、streamableHttp、websocket
command字符串或数组stdio 模式下启动命令
args数组命令参数
env对象stdio 子进程环境变量
cwd字符串stdio 子进程工作目录
url字符串SSE、Streamable HTTP、WebSocket 的目标地址
headers对象HTTP 请求头
enabled布尔值是否启用

当文件不存在时，系统会自动创建默认空配置；当文件损坏时，系统会降级为空服务器列表并记录错误日志。

插件扫描 ​

当前实现中，MCP Server 不是通过文件系统扫描自动发现的，而是通过显式配置管理。也就是说，“插件扫描”在当前代码中表现为 配置驱动的 Server 列表，而不是目录扫描。

如果需要未来扩展为插件扫描，可考虑以下方向：

  • 扫描固定目录下的 MCP Server 包。
  • 解析包元数据中的 MCP 入口。
  • 自动生成 mcp_servers.json 条目。
  • 增加依赖安装和版本校验。

但当前仓库并未实现该能力，因此文档应明确：MCP 工具发现是配置驱动，而非文件系统扫描驱动。

依赖解析 ​

MCP 客户端依赖 @modelcontextprotocol/sdk 提供的 Client 和多种 Transport。这些依赖由 Agent 包的 package.json 管理。扩展端不直接依赖 MCP SDK，只通过 HTTP API 与 Agent 交互。

配置管理系统 ​

配置文件位置 ​

MCP 配置存储在用户主目录下的 .ai-helper-agent/mcp_servers.json。该路径由 homedir() 拼接得到，跨平台安全。

配置结构 ​

配置根对象包含 servers 数组。每个 Server 至少需要：

  • id：唯一标识。
  • transport：传输类型。
  • 根据传输类型必填：
    • stdio：command。
    • sse、streamableHttp、websocket：url。

可选字段包括 name、args、env、cwd、headers、enabled。

环境变量支持 ​

对于 stdio 传输，env 字段会被透传到子进程环境。这意味着敏感值可以通过 MCP Server 配置传入，而不必写入 Shell 配置。

对于 HTTP 类传输，headers 字段可用于携带认证头或其他请求头。

写保护与并发控制 ​

配置写入使用链式 Promise 实现的写锁，保证多次写入串行化。这避免了多个请求同时写 JSON 文件导致内容损坏。

缓存策略 ​

配置加载使用 mtime 缓存：

  • 如果文件修改时间未变，直接返回内存缓存。
  • 如果文件不存在，创建默认配置。
  • 如果解析失败，返回空服务器列表。

工具生命周期管理 ​

启动时初始化 ​

Agent 启动流程如下：

  1. 创建 HTTP 服务器。
  2. 设置各子模块的语言。
  3. 启动配对码轮换。
  4. 启动回收站定期清理。
  5. 异步初始化 MCP 注册表和 Skill 注册表。
  6. 启动 Skill 目录监听。

MCP 初始化不会阻塞 HTTP 服务启动，即使 MCP 连接失败也不会阻止 Agent 正常运行。

运行时更新 ​

运行时可通过 HTTP API 动态管理 MCP Server：

  • 添加 Server。
  • 删除 Server。
  • 连接 Server。
  • 断开 Server。
  • 切换启用状态。
  • 调用工具。

当 Server 被禁用时，注册表会先断开已有连接，确保工具立即不可用。

优雅关闭 ​

Agent 的 shutdown 函数负责：

  • 停止配对码轮换。
  • 停止回收站清理。
  • 中止 RAG 依赖安装。
  • 终止运行中的进程。
  • 关闭所有 MCP 连接。
  • 强制断开 WebSocket 客户端。
  • 销毁活跃 HTTP Socket。
  • 等待服务器关闭。
  • 清理 PID 文件。
  • 退出进程。

工具冲突解决策略 ​

当前实现通过以下机制避免工具冲突：

冲突场景解决方式
同一 Server 下同名工具MCP Server 自身需保证工具名唯一；Agent 不做二次去重。
不同 Server 下同名工具扩展端使用 mcp_{serverId}_{toolName} 作为最终工具 ID，避免冲突。
重复注册扩展端使用 mcpToolIds Set 去重，已注册工具跳过。
禁用 Server 的工具扩展端构建禁用 Server ID 集合，跳过对应工具。
重复加载loadMcpTools 使用 mcpLoadLock 串行化，避免并发加载覆盖。
卸载旧工具unloadMcpToolsInternal 清理 RAW_TOOLS、BUILTIN_TOOLS、执行映射和处理器。

版本兼容性与能力检查 ​

MCP 客户端版本 ​

MCP 客户端声明自身版本为 1.3.4，用于向 MCP Server 报告客户端身份。

服务端能力探测 ​

连接成功后，客户端会获取：

  • getServerVersion()
  • getServerCapabilities()

这些信息保存在 serverInfo 中，可用于后续扩展能力判断。当前实现没有对能力做严格断言，而是假设支持标准工具枚举和调用。

工具列表容错 ​

如果 listTools 返回空或无效结构，客户端会将 tools 设为空数组，而不是抛出异常。这样即使某个 MCP Server 行为不规范，也不会阻断整个注册表。

扩展端兼容性 ​

扩展端对 Agent 的 MCP 能力做了容错处理：

  • 如果 Agent 不支持 MCP 或返回空工具列表，扩展端跳过注册。
  • 如果 Agent 不可达，扩展端记录警告日志。
  • 全局 mcpEnabled 开关可完全关闭 MCP 工具加载。

性能与可靠性特征 ​

性能特征 ​

  • MCP 连接在 Agent 启动后异步初始化，不阻塞 HTTP 服务。
  • 扩展端加载工具时使用互斥锁，避免并发加载。
  • 配置加载使用 mtime 缓存，减少磁盘 IO。
  • 配置写入使用链式 Promise 锁，避免并发写竞争。
  • 工具调用走 Agent 单进程，扩展端不直接管理 MCP 子进程。

可靠性特征 ​

  • MCP 连接失败不会中断 Agent 启动。
  • 工具列表为空时扩展端静默跳过。
  • 配置解析失败时降级为空服务器列表。
  • 断开连接时捕获异常，避免清理过程抛错。
  • 关闭流程有 10 秒超时保护，防止进程挂起。

潜在优化点 ​

  • 当前注册表没有主动重连机制，Server 断开后不会自动恢复。
  • 工具 Schema 压缩逻辑不在本文件中，但扩展端会对描述和参数进行压缩，可能影响调试可读性。
  • 如果 MCP Server 数量很大，每次 getMcpTools 都会遍历所有已连接客户端，可考虑缓存扁平化工具列表。

结论 ​

AI Helper 的 MCP 工具注册与发现机制以 配置驱动 为核心，通过 Agent 端统一管理 MCP Server 连接，并通过扩展端动态注入工具定义，实现了浏览器边界之外的能力扩展。

其设计优点包括：

  • 多传输协议支持。
  • 多 Server 并行连接。
  • 工具 ID 隔离避免冲突。
  • 配置缓存与写锁保证一致性。
  • 启动非阻塞、关闭优雅。
  • 扩展端与 Agent 解耦，通过 HTTP API 通信。

需要注意的限制包括：

  • 当前无自动插件扫描。
  • 无自动重连机制。
  • 无严格的 MCP 能力版本断言。
  • 工具 Schema 压缩可能影响调试体验。

未来若需要增强，可优先考虑：

  • 增加 MCP Server 自动发现。
  • 增加连接健康检查和自动重连。
  • 增加能力协商和版本兼容性检查。
  • 增加工具调用限流和超时控制。
  • 增加 MCP 工具调用审计日志。
