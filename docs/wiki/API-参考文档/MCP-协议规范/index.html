引言 ​

本规范面向 AI Helper Agent 的 MCP（Model Context Protocol）扩展能力，说明当前实现如何发现、连接、调用第三方 MCP Server，并把其工具注入到统一工具列表中。文档同时给出协议版本兼容性策略、工具定义格式、消息与错误处理约定、工具注册机制、以及 Python/Node.js 客户端集成参考路径。

项目结构 ​

Agent 端的 MCP 功能集中在 agent/src/mcp 三个模块中：

  • client.js：封装单个 MCP Server 的连接、传输层选择、工具列表获取与工具调用。
  • registry.js：维护多个 MCP Client 实例，提供启动时自动连接、状态查询、扁平化工具列表和工具调用路由。
  • mcp-config.js：持久化 MCP Server 配置（~/.ai-helper-agent/mcp_servers.json），提供增删改查与写锁保护。

核心组件 ​

  • McpClient：负责单一 MCP Server 的生命周期，包括传输层创建、连接、工具发现、工具调用与断开。
  • Registry：集中管理所有已连接的 McpClient，暴露初始化、状态查询、工具列表聚合、工具调用入口。
  • Config：负责 MCP Server 配置的加载、保存、添加、删除、启用/禁用，并提供内存缓存与写入互斥锁。

关键职责边界：

  • 协议细节由 SDK 与 client.js 承担；
  • 多 Server 并发与工具聚合由 registry.js 承担；
  • 配置持久化与权限校验由 mcp-config.js 与上层 server 路由承担。

架构总览 ​

Agent 作为 MCP 客户端，通过 JSON-RPC 2.0 与外部 MCP Server 通信。Agent 启动时自动连接所有启用的 MCP Server，拉取工具列表并合并为全局工具集；当扩展端需要执行某个 MCP 工具时，Agent 将请求转发给对应 Server，再把结果返回给扩展端。

详细组件分析 ​

组件一：McpClient ​

McpClient 是单个 MCP Server 的抽象，封装了以下能力：

  • 根据配置选择传输层：stdio、SSE、Streamable HTTP、WebSocket。
  • 使用 SDK 的 Client 进行连接，获取服务端版本、能力与工具列表。
  • 调用工具时把 SDK 返回的结构转换为统一的 {success, content, raw} 或失败对象。
  • 提供 getStatus() 用于对外展示连接状态、工具数量与服务端信息。

关键行为说明：

  • 连接成功后会调用 listTools({}) 获取工具列表，并缓存到 this.tools。
  • 工具调用失败时，优先使用 SDK 返回的 error.message，否则回退到本地翻译的错误提示。
  • 工具返回内容按 type === 'text' 过滤后拼接成文本字符串，便于模型消费。

组件二：MCP 工具注册表 Registry ​

Registry 维护一个 Map<serverId, McpClient>，提供：

  • 启动时自动连接所有 enabled: true 的 MCP Server。
  • 查询所有已连接 Server 的状态与工具。
  • 扁平化输出工具列表，包含 serverId、serverName、name、description、inputSchema。
  • 路由工具调用到具体 Server。

性能与可靠性 ​

  • 配置读写采用内存缓存与文件 mtime 判断，避免频繁磁盘 I/O。
  • 配置写入使用 Promise 链式写锁，防止并发写导致数据损坏。
  • 每个 HTTP 请求处理器有异常捕获，避免单个错误拖垮服务。
  • MCP 子进程与命令执行共享 Agent 的安全分级与审计日志体系。

故障排查指南 ​

常见现象与定位建议：

  • 新增 MCP Server 后无法连接：
    • 检查 mcp_servers.json 中 id、command 或 url 是否填写正确。
    • stdio 模式需确保命令可执行；HTTP 模式需确保 URL 可达。
    • 查看 Agent 控制台日志中的 [MCP] 前缀信息。
  • 工具列表为空：
    • 确认 Server 已成功连接；getMcpServersStatus() 会返回 connected 与 toolCount。
    • 检查 MCP Server 是否正确实现 tools/list。
  • 工具调用失败：
    • 查看 callTool 返回的 error 字段；SDK 层错误会被透传。
    • 若 MCP Server 返回结构化错误，优先使用其 message。
  • 配置修改不生效：
    • 确认文件已保存且 mtime 发生变化；必要时重启 Agent 以重新加载配置。

结论 ​

当前 Agent 对 MCP 的实现以 SDK 为核心，围绕 client.js、registry.js、mcp-config.js 形成“单 Server 客户端 + 多 Server 注册表 + 配置持久化”的稳定结构。它支持多种传输方式，具备自动发现工具、统一工具聚合、安全校验与 i18n 能力，适合扩展第三方工具生态。未来升级方向聚焦于协议 Modern 模式的 Dual-era 兼容与无状态化迁移。

协议版本兼容性 ​

  • 当前 SDK 版本为 @modelcontextprotocol/sdk@^1.29.0，运行在 Legacy 模式。
  • 协议演进时间线包括 2024-11-05、2025-03-26、2025-06-18、2025-11-25，以及 2026-07-28 的无状态化版本。
  • 当前实现通过 SDK 内部协商完成版本选择；尚未实现显式的 Dual-era 探测逻辑。
  • 官方建议在未来引入 server/discover 与 _meta 无状态请求，并对弃用特性保留 12 个月窗口。

工具定义格式 ​

Agent 从 MCP Server 拉取的每个工具至少包含：

  • name：工具名称。
  • description：工具描述。
  • inputSchema：参数 JSON Schema；若缺失则回退为 { type: 'object', properties: {} }。

Agent 向外暴露的工具元数据包含：

  • serverId：来源 Server 标识。
  • serverName：显示名称。
  • name、description、inputSchema：来自 MCP Server 的工具定义。

返回值方面，Agent 对 MCP 工具调用的统一包装为：

  • 成功：{ success: true, content: string, raw: object }。
  • 失败：{ success: false, error: string }。

消息格式与错误处理 ​

  • MCP 客户端与服务端之间使用 JSON-RPC 2.0。
  • 连接阶段：connect() → getServerVersion() → getServerCapabilities() → listTools({})。
  • 调用阶段：callTool({ name, arguments })。
  • 错误处理：
    • 连接失败：返回 { success: false, error }。
    • 工具调用失败：优先使用 SDK 返回的 error.message，否则使用本地翻译错误。
    • 未连接时调用工具：直接返回未连接错误。
flowchart TD
Entry["调用工具入口"] --> CheckConn{"Server 已连接?"}
CheckConn --> |否| ErrNotConnected["返回未连接错误"]
CheckConn --> |是| CallSdk["调用 SDK callTool"]
CallSdk --> HasError{"SDK 返回 error?"}
HasError --> |是| ErrSdk["返回 success=false + error.message"]
HasError --> |否| BuildResult["提取 text 内容并构建结果"]
BuildResult --> Ok["返回 success=true + content"]

工具注册机制 ​

  • 动态发现：启动时自动连接所有启用的 MCP Server，并调用 listTools 获取工具。
  • 自动加载：initializeMcpRegistry() 遍历配置，逐个连接并注册到 clients Map。
  • 配置管理：mcp_servers.json 支持添加、删除、启用/禁用 Server；UI 通过 /api/mcp/servers 等接口操作。
  • 安全校验：stdio 模式下会对 command + args 做命令安全分级检查，高危命令直接拒绝，灰名单命令要求确认。

Python 客户端集成参考 ​

虽然仓库未内置 Python MCP Server 示例，但 Agent 的 MCP 客户端支持 stdio 传输，因此可以在 Python 中实现一个遵循 MCP 协议的命令行程序，并通过 Agent 配置中的 command 与 args 启动。典型步骤：

  • 安装官方 MCP SDK。
  • 实现 initialize、tools/list、tools/call。
  • 通过标准输入输出发送 JSON-RPC 2.0 消息。
  • 在 Agent 配置中将 command 设为 python，args 设为 -m your_mcp_server。

注意：Agent 会对 stdio 命令执行安全分级检查，避免 MCP 成为命令管控后门。

Node.js 客户端集成参考 ​

Agent 自身就是 MCP 客户端，可直接复用其 McpClient 类：

  • 构造 serverConfig，包含 id、name、command 或 url、transport、env、headers。
  • 调用 connect() 建立连接并拉取工具列表。
  • 调用 callTool(name, args) 执行工具。
  • 调用 disconnect() 释放资源。

最佳实践 ​

  • 为每个 MCP Server 设置唯一 id 与可读 name，便于区分来源。
  • 优先使用 stdio 传输开发调试，生产环境可使用 Streamable HTTP 或 WebSocket。
  • 敏感 Token 通过环境变量传入，不要硬编码在配置文件中。
  • 工具描述应清晰说明用途、触发条件与参数含义，有助于模型预筛选。
  • 对长耗时工具，建议在 MCP Server 侧做好超时与重试控制。
  • 定期清理不再使用的 MCP Server，减少子进程与工具上下文开销。
