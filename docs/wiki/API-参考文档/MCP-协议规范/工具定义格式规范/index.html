引言 ​

本规范面向 MCP（Model Context Protocol）工具的开发者与维护者，说明在 AI Helper Agent 与扩展端协作体系中，MCP 工具的定义格式、参数校验规则、返回结构、注册发现流程以及生命周期管理方式。文档以仓库中已实现的 MCP Client、MCP Registry、测试服务器和背景工具执行器为依据，避免臆造协议字段；对尚未实现的能力仅给出建议性说明，并明确标注来源。

核心概念与术语 ​

  • MCP Server：提供工具的外部服务，可通过 stdio、SSE、Streamable HTTP 或 WebSocket 与 Agent 通信。
  • MCP Client：Agent 内部封装的 MCP 客户端实例，负责建立连接、获取工具列表、转发工具调用。
  • MCP Registry：维护所有已连接 MCP Server 的工具集合，并提供统一查询与调用接口。
  • Tool Definition：MCP Server 暴露的工具描述，包含名称、描述、输入参数 Schema。
  • Tool Call：通过 MCP 协议调用的具体工具执行过程。
  • Background Tool：扩展端将 MCP 工具包装为本地可执行函数，供 ReAct 推理循环使用。

参数 Schema 规范 ​

MCP 工具的输入参数采用 JSON Schema 风格定义。当前实现中，Agent 侧对 inputSchema 的处理偏保守：如果 MCP Server 未返回 inputSchema，则默认使用 { type: 'object', properties: {} }。

推荐的最小结构 ​

字段类型是否必需说明
type字符串否通常为 object
properties对象否参数键到属性定义的映射
required字符串数组否必填参数列表
description字符串否参数整体说明

属性定义常用字段 ​

字段类型说明
type字符串如 string、number、boolean、object
description字符串参数用途说明
enum数组可选值枚举
default任意类型默认值（Agent 侧未强制校验，建议由 MCP Server 处理）

验证行为 ​

  • Agent 侧不会在 MCP 调用前对参数做严格 JSON Schema 校验。
  • 参数校验主要由 MCP Server 自行实现；Agent 侧只负责转发 arguments。
  • Skill 系统的参数校验可作为参考：它支持 type、required、基础类型转换，但不等同于 MCP 参数校验器。

返回值格式规范 ​

MCP 工具调用最终由扩展端统一包装为工具执行结果。其核心契约如下：

成功响应 ​

字段类型含义
success布尔值表示调用是否成功
content字符串文本化后的工具输出
tool_call_id字符串工具调用标识，由扩展端传入

Agent 侧从 MCP Server 返回的 content 中提取 type === 'text' 的内容并拼接为字符串。

失败响应 ​

字段类型含义
success布尔值通常为 false
error字符串错误信息，可能来自 MCP Server 或 Agent 层

MCP Server 原始返回结构 ​

MCP Server 应遵循 MCP SDK 约定：

  • 成功时返回 result.content，其中至少包含一个 type: 'text' 的内容项。
  • 失败时可返回 result.error，Agent 侧会读取 error.message。

工具生命周期管理 ​

MCP 工具的生命周期包括：配置加载、连接建立、工具发现、动态注册、调用、断开与销毁。

启动阶段 ​

  1. Agent 启动时加载 MCP 配置。
  2. 遍历启用的 MCP Server。
  3. 创建 McpClient 并连接。
  4. 调用 listTools 获取工具列表。
  5. 将工具注册到全局状态。

运行阶段 ​

  1. 扩展端请求 MCP 工具列表。
  2. Agent 返回扁平化工具定义。
  3. 扩展端将 MCP 工具包装为本地工具处理器。
  4. 调用时经 AgentClient.callMcpTool 转发至对应 Server。

关闭阶段 ​

  1. 显式断开某个 MCP Server。
  2. 清理客户端实例与工具缓存。
  3. Agent 关闭时批量断开所有连接。

性能与上下文压缩 ​

扩展端会对 MCP 工具的 inputSchema 进行压缩，防止工具元数据撑爆上下文窗口。压缩策略包括：

  • 移除 $schema、$ref、definitions、additionalProperties 等冗余字段。
  • 截断过长的描述。
  • 限制嵌套深度。
  • 当参数数量超过上限时，保留前若干参数，并将剩余参数合并为 additionalParams。
flowchart TD
Start(["接收 inputSchema"]) --> CheckEmpty{"是否为空或非对象?"}
CheckEmpty --> |是| ReturnDefault["返回空对象 Schema"]
CheckEmpty --> |否| StripFields["移除冗余字段"]
StripFields --> SetType["确保 type 为 object"]
SetType --> CompressDesc["压缩 description"]
CompressDesc --> CompressProps["压缩 properties"]
CompressProps --> CountProps{"参数数量是否超限?"}
CountProps --> |是| MergeExtra["合并多余参数为 additionalParams"]
CountProps --> |否| KeepProps["保留原 properties"]
MergeExtra --> ReturnCompressed["返回压缩后的 Schema"]
KeepProps --> ReturnCompressed
ReturnDefault --> End(["结束"])
ReturnCompressed --> End

开发最佳实践 ​

  • 明确工具职责：每个 MCP 工具应聚焦单一能力，避免把复杂业务拆成模糊的大工具。
  • 使用 JSON Schema 描述参数：即使 Agent 不强制校验，清晰的 inputSchema 也能帮助 LLM 正确传参。
  • 优先返回文本内容：MCP Client 会提取 type: 'text' 的内容，因此建议将结构化结果序列化为可读文本。
  • 区分成功与失败语义：成功时返回 result.content，失败时返回 result.error.message，便于 Agent 层统一包装。
  • 控制参数数量：避免暴露过多参数；必要时拆分工具或使用枚举减少组合爆炸。
  • 保持工具名稳定：name 是工具识别关键字段，频繁变更会影响历史调用与调试。
  • 利用测试服务器验证：使用仓库中的 MCP 测试服务器快速验证 tools/list 与 tools/call 行为。
  • 注意 Agent 进程重启约束：Agent 源码修改后必须重启进程，新接口才生效。

常见陷阱与排错指南 ​

  • 未连接就调用工具：Agent 会在 callTool 前检查连接状态，返回 success: false 与错误消息。
  • MCP Server 未返回工具列表：Agent 会将 tools 置为空数组，扩展端不会注册任何 MCP 工具。
  • MCP Server 返回非文本内容：Agent 只拼接 type === 'text' 的内容，其他类型会被忽略。
  • 参数缺失或类型错误：Agent 不做强校验，需由 MCP Server 自行处理；建议在 Server 层返回明确的错误信息。
  • 配置写入冲突：MCP 配置保存使用写锁，避免并发写入导致损坏。
  • 扩展端上下文被撑爆：注意 compressMcpSchema 的参数截断行为，避免暴露超大 Schema。
  • Agent 端口占用或服务异常：Agent 启动时会检测端口占用并记录日志，排查时应关注服务启动日志。

结论 ​

本规范总结了 AI Helper 项目中 MCP 工具的定义格式、参数 Schema 约定、返回值结构、生命周期管理与常见问题处理方式。实际实现中，Agent 侧对 MCP 工具的定义较为轻量：重点在于 name、description、inputSchema 与 content 文本输出。开发者应优先保证工具语义清晰、参数描述准确、返回内容可读，并通过测试服务器与 Agent 日志完成端到端验证。对于更严格的 JSON Schema 校验、默认值处理与复杂返回结构，建议由 MCP Server 自行实现，并在 Agent 层做好错误包装与上下文压缩。
