引言 ​

本文面向 Chrome Extension（Manifest V3，版本 2.3.1）与独立本地 Agent（Node.js，版本 2.3.1）的双进程架构，系统性说明以下能力：

  • chrome.runtime.sendMessage 与 chrome.runtime.onMessage 的同步/异步使用方式。
  • Content Script 中基于 Map 的消息路由表结构及 O(1) 分发逻辑。
  • Background Service Worker 作为扩展内部消息中枢的职责。
  • 扩展端通过 local-agent-client.js 与 Agent 端 server.js 之间的 HTTP 与 WebSocket 契约。
  • 消息超时、可达性缓存、SW 保活、Agent 重启等运行时约束。
  • 实际代码路径引用，便于读者直接定位实现。

本项目是双进程架构：Chrome 扩展端位于 src/，Agent 端入口为 agent/src/server.js。两端版本号保持同步，文档以 2.3.1 为准。Agent 源码修改后必须重启进程，新接口才生效。

项目结构与通信边界 ​

扩展端按 MV3 Service Worker 组织，核心通信边界如下：

  • 网页脚本 / Content Script：运行在页面上下文中，负责 DOM 操作、页面信息提取、用户交互。
  • Background Service Worker：扩展全局上下文，负责消息路由、工具调度、Agent 客户端封装、侧边栏控制、定时任务等。
  • Side Panel / Options / Offscreen：扩展 UI 层，通过 chrome.runtime.sendMessage 与 Background 通信。
  • Agent 服务：独立 Node.js 进程，提供文件系统、命令执行、Skill、MCP、RAG 等能力，暴露 HTTP API 与 WebSocket。

Chrome 扩展消息模型：sendMessage 与 onMessage ​

同步消息 ​

当接收方在 onMessage 处理器中直接调用 sendResponse(result) 并返回 undefined 时，发送方的回调立即拿到结果。适用于轻量、无网络 IO 的操作。

示例路径：

  • Content Script 同步处理简单查询类消息。
  • Background 向 Side Panel 或 Options 广播状态变更。

参考实现位置：

  • src/shared/utils.js#L74-L78
  • src/side_panel/schedule-panel.js#L134-L136

异步消息 ​

当处理器返回 true，或通过 Promise 调用 sendResponse，表示消息通道保持开放，后续再回复。适用于：

  • 需要等待 DOM 操作完成。
  • 需要等待网络请求或子任务完成。
  • 需要维持长连接（如 keepalive port）。

参考实现位置：

  • src/content/index.js#L210-L246
  • src/background/index.js#L140-L218

关键行为总结 ​

场景发送方接收方返回值约定
轻量同步响应chrome.runtime.sendMessage(msg, cb)onMessage 中直接 sendResponse(data)同步返回
异步响应chrome.runtime.sendMessage(msg, cb)onMessage 中 Promise.then(sendResponse) 并返回 true延迟回复
长连接chrome.runtime.connect(portName)onConnect 监听端口双向 postMessage
跨 Tab 定向chrome.tabs.sendMessage(tabId, msg)目标 Tab 的 Content Script onMessage同 sendMessage

Content Script 到 Background Service Worker 的消息路由表 ​

Content Script 使用一个集中式 HANDLERS Map，将 message.type 映射到具体处理器函数。该设计具备以下特点：

  • O(1) 查找：通过对象键直接定位处理器。
  • 分类清晰：页面读取、页面交互、表单输入、信息提取、媒体输出、异步工具等分组明确。
  • 异步标记集合：ASYNC_HANDLERS 声明哪些类型需要保持消息通道开放。
  • 顶层帧限制：TOP_FRAME_ONLY_TYPES 避免 iframe 抢占响应。
flowchart TD
Start["收到 chrome.runtime.onMessage"] --> CheckTop["是否 TOP_FRAME_ONLY 且非顶层帧？"]
CheckTop --> |是| Ignore["忽略消息"]
CheckTop --> |否| Lookup["HANDLERS[message.type]"]
Lookup --> Found{"找到处理器？"}
Found --> |否| Exit["不处理"]
Found --> |是| CallHandler["调用 handler(message)"]
CallHandler --> AsyncCheck{"是否 ASYNC_HANDLERS 或返回 Promise？"}
AsyncCheck --> |是| KeepOpen["return true<br/>Promise.then(sendResponse)"]
AsyncCheck --> |否| SyncReply["sendResponse(result)"]

扩展端与 Agent 端的 HTTP/WebSocket 通信契约 ​

总体契约 ​

扩展端通过 local-agent-client.js 统一封装对 Agent 的 HTTP 与 WebSocket 调用；Agent 端由 server.js 提供 HTTP Router 与 WebSocket 支持。所有需认证的请求携带 Authorization: Bearer <token>。

BG->>Client : 调用 execCommand / readFile / getMcpTools 等
Client->>Client : agentRequest(path, body, method, timeoutMs)
Client->>Agent : fetch(url, { Authorization : Bearer token })
Agent-->>Client : JSON { success, ... }
Client-->>BG : 返回结果或错误

WebSocket 契约 ​

WebSocket 用于命令执行的实时输出流。扩展端通过 createExecWebSocket(wsUrl, onMessage, onClose, onError) 建立连接，Token 通过 URL 参数附加。

关键点：

  • Token 从当前活跃 Agent 配置中获取。
  • 若 Agent 已知不可达，直接走错误回调，避免无效连接。
  • 空闲超时由调用方统一管理，避免双重超时冲突。
  • 连接成功 resolve WebSocket 实例，失败 reject 并触发 onError。

Client->>WS : new WebSocket(authenticatedUrl)
WS-->>Client : onopen → resolve(ws)
WS-->>Executor : onmessage(JSON)
WS-->>Executor : onclose → onClose()
WS-->>Executor : onerror → onError(error)

认证与安全 ​

  • Agent 端对大多数接口要求 Authorization: Bearer <token>。
  • CORS 仅放行 chrome-extension:// 来源。
  • 配对接口 /api/pair 无需认证，但会记录 extensionId。
  • 心跳接口 /api/heartbeat 刷新在线状态，不返回敏感信息。

超时、重试与连接状态管理 ​

消息超时 ​

  • HTTP 请求通过 AbortController 实现超时，默认 60 秒，部分接口（如下载）延长至 120 秒。
  • WebSocket 空闲超时由调用方统一管理，避免与连接层双重超时冲突。

参考实现位置：

  • src/background/local-agent-client.js#L410-L442
  • src/background/local-agent-client.js#L662-L728

重试机制 ​

  • 代码未实现自动重试循环，而是通过可达性缓存快速失败，避免阻塞。
  • 用户可通过“触发健康检查”手动刷新状态。

参考实现位置：

  • src/background/local-agent-client.js#L405-L408
  • src/background/index.js#L1817-L1822

连接状态管理 ​

  • Background 维护 _agentReachability 内存缓存，按 agentId 区分可达性。
  • SW 保活通过 side panel 的 keepalive port 防止被系统回收。
  • Agent 重启/更新后需重新配对或刷新 token。

参考实现位置：

结论 ​

本项目的消息通信机制围绕三层展开：

  1. 扩展内部：Content Script 通过集中式路由表与 Background Service Worker 通信，支持同步与异步模式。
  2. 扩展与 Agent：Background 通过 local-agent-client.js 封装 HTTP 与 WebSocket，统一认证、超时与可达性管理。
  3. Agent 服务端：提供 RESTful API 与实时命令输出流，支持文件、命令、Skill、MCP、RAG 等能力。

在实际使用中，应重点关注：

  • 消息类型定义与路由一致性。
  • 异步处理器正确返回 true 或使用 Promise。
  • Agent 连接状态与 token 有效性。
  • SW 生命周期与保活机制。
  • 大消息截断与性能优化。
