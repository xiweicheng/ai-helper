简介 ​

本参考文档面向“长期记忆管理”和“检索增强生成（RAG）知识库”两套能力，覆盖以下目标：

  • 说明记忆管理端点 /api/memory/add、/api/memory/query、/api/memory/tags、/api/memory/tier 的调用方式、参数、状态码与错误处理。
  • 说明 RAG 检索端点 /api/rag/search、/api/rag/index、/api/rag/documents 的行为、配置项与使用示例。
  • 解释混合检索引擎：语义搜索、关键词匹配、结果重排序（RRF）。
  • 说明向量嵌入生成、文档分块策略与索引构建流程。
  • 提供完整的 API 调用示例、参数配置选项、性能优化建议与故障诊断方法。

本项目采用双进程架构：Chrome 扩展端（Manifest V3）通过本地 HTTP/WebSocket 调用 Agent（Node.js）提供的能力；Agent 源码修改后必须重启进程，新接口才生效。

项目结构 ​

记忆与 RAG 功能集中在 Agent 端的 agent/src/memory 与 agent/src/rag 两个子系统中，由统一 HTTP 服务器 server.js 进行认证、CORS、请求体解析与路由分发。

核心组件 ​

  • HTTP 服务器与认证层：负责 Bearer Token 校验、CORS、JSON body 解析、Multipart 上传、健康检查与通用错误响应。
  • 记忆服务：实现记忆的增删改查、会话级去重、关键词检索、可选语义通道、标签名次加成、价值评估与压缩淘汰。
  • RAG 路由与管理器：实现知识库 CRUD、文档导入、单库/跨库检索、安装检测、嵌入连通性测试。
  • 混合检索器：向量相似度 + 关键词命中抬分 + 旁路探测 + 阈值过滤。
  • 标签与召回档位：标签在有查询时仅做名次加成；无查询时作为唯一选择器；召回档位根据 embedding 配置与 RAG 依赖决定 none/remote/local。

详细组件分析 ​

记忆管理端点 ​

记忆端点由 memoryDispatch 统一分发，支持 store/recall/manage/injectSelect/reindex 等动作，并附带 embedding 配置与探活端点。

/api/memory/store（添加/更新/删除记忆） ​

  • 方法：POST
  • 用途：新增事实或摘要、更新已有记忆、按 id 删除记忆。
  • 关键行为：
    • 写入前校验 action/type/content/importance 等字段。
    • 对 add/update 内容执行注入模式拦截，命中提示注入短语直接拒绝。
    • 带 sessionId 的写入有进程内频率上限，防止批量投毒。
    • 写成功后异步补向量（懒补），失败不阻塞主流程。
    • 删除时会同步清理派生向量缓存，避免孤儿向量。
  • 成功响应：{ success: true, message, memory/action/stats }
  • 业务失败：HTTP 400，{ success: false, error, code? }
  • 未匹配路径：HTTP 404，{ success: false, error: "unknownApiPath" }

调用示例（概念描述）：

  • 添加事实：POST /api/memory/store，body 包含 action: "add"、type: "fact"、content、可选 tags、importance、sourceSessionId。
  • 更新记忆：POST /api/memory/store，body 包含 action: "update"、memoryId、可选 content/tags/importance/category/title。
  • 删除记忆：POST /api/memory/store，body 包含 action: "delete"、memoryId。

/api/memory/recall（查询记忆） ​

  • 方法：POST
  • 用途：从长期记忆中检索相关信息，支持关键词通道与可选语义通道融合。
  • 关键行为：
    • 支持 query、tags、memoryType、limit。
    • 无向量通道时走纯关键词匹配；有向量通道时走 RRF 排名融合。
    • 标签在有查询时仅做名次加成；无查询时作为唯一选择器。
    • 会话级去重：同一 sessionId 重复返回的记忆会被优先替换为未召回过的条目。
    • 访问计数在收尾阶段重读真源后安全写回。
  • 成功响应：{ success: true, message, results, total, query, tier, vectorMatched }
  • 业务失败：HTTP 400，{ success: false, error }

调用示例（概念描述）：

  • 普通查询：POST /api/memory/recall，body 包含 query、可选 tags、memoryType、limit、sessionId。

/api/memory/manage（审查与压缩） ​

  • 方法：POST
  • 用途：review（计算价值分数并返回淘汰建议）、compact（淘汰低价值记忆）。

关于 /api/memory/add、/api/memory/query、/api/memory/tags、/api/memory/tier ​

  • 代码中的记忆业务入口是 /api/memory/store、/api/memory/recall、/api/memory/manage、/api/memory/embedding-config、/api/memory/test-embedding、/api/memory/vector-status、/api/memory/reindex。
  • 扩展端工具层将 store、recall、manage 映射到对应端点；inject 由系统提示词分级注入直接调用。
  • 因此，“添加记忆”应使用 /api/memory/store（action=add），“查询记忆”应使用 /api/memory/recall，“标签管理”通过 recall 的 tags 参数与 manage 的 review/compact 配合，“层级管理”通过 embedding-config 与 tier 判定逻辑控制。

RAG 检索端点 ​

RAG 路由仅在 RAG 依赖可用时按需加载，所有受保护端点需 Bearer Token。

/api/rag/search（跨知识库检索） ​

  • 方法：POST
  • 用途：跨多个知识库执行语义检索；未指定 collectionIds 时搜索全部启用库。
  • 参数：
    • collectionIds：数组，显式指定要检索的知识库 ID。
    • query：检索文本。
    • topK：返回结果数量预算。
    • threshold：语义阈值。
  • 行为：
    • 显式 IDs 原样放行，即使库被停用也可检索（@ 手动引用链路）。
    • 未指定 IDs 时跳过 disabled 库。
    • 多库时 topK 配额按库均分，保证每个被引用的库都有结果。
  • 成功响应：{ success: true, results, total, hasContext, fallback }
  • 业务失败：HTTP 400，{ success: false, error, code? }

调用示例（概念描述）：

  • 跨库检索：POST /api/rag/search，body 包含 collectionIds、query、topK、threshold。

混合检索引擎 ​

混合检索由两条通道组成：

  • 语义通道：使用 embeddingProvider.embedQuery 生成查询向量，再通过向量存储检索候选。
  • 关键词通道：自建中英文匹配，英文/数字按词边界匹配，中文取最长命中片段；高频单元剔除；命中 chunk 保底分 + 单元加分。
  • 重排序：RRF（Reciprocal Rank Fusion），关键词与向量各排各的名次，按 1/(60 + rank) 合并，不比较绝对分数。
flowchart TD
Start(["开始检索"]) --> Embed["生成查询向量"]
Embed --> VectorSearch["向量检索 topK*2"]
VectorSearch --> KeywordBoost["关键词命中增强"]
KeywordBoost --> Threshold["阈值过滤"]
Threshold --> Empty{"结果为空？"}

文档分块策略 ​

  • 默认 chunkSize=400，overlap=80，separator='\n\n'。
  • 先按段落切，再合并到接近 chunkSize；单段超长强制按字符切；硬上限 500 字符。
  • 返回 chunks 包含 startPos/endPos，为 BM25 混合检索预留。

索引构建流程 ​

  • 文档解析：text/md/json/csv/html/pdf/office 等格式由对应 parser 输出纯文本。
  • 分块：chunker 按策略切分。
  • 向量化：embeddingProvider 生成向量。
  • 存储：VectraStore 使用 LocalIndex，beginUpdate/endUpdate 事务包裹逐条 upsertItem，失败 cancelUpdate。
  • 重建：向量空间或分块参数变更时后台自动重建，临时目录重放 → 原子换入。

性能考虑 ​

  • 记忆侧：
    • 向量嵌入调用带 8 秒超时，失败降级到关键词通道。
    • 懒补向量不 await，避免每次 store 增加网络往返。
    • recall 分三阶段：锁内只读、锁外补齐、锁内收尾，避免外部嵌入拖垮全进程。
    • 标签在有查询时仅做名次加成，避免三个硬门槛叠加导致误杀。
  • RAG 侧：
    • 关键词扫描限制 KEYWORD_SCAN_LIMIT，超过则跳过关键词通道防止大库卡顿。
    • 旁路探测放宽阈值区分“无数据”与“被过滤”。
    • 多库检索 topK 按库均分，避免高得分库垄断结果。
  • 通用：
    • MAX_BODY_SIZE 限制 JSON body 大小。
    • 流式上传支持二进制，避免 base64 膨胀。
    • 认证冷却与操作防重入，防止 DoS。

故障诊断指南 ​

常见错误与处理方式：

  • 401 未认证：缺少 Authorization: Bearer <token>。
  • 403 无效 Token：Token 校验失败。
  • 400 业务错误：参数缺失、JSON 解析失败、Multipart 解析失败、RAG 不支持类型、记忆注入模式拦截等。
  • 404 未知路径：记忆端点未匹配或 RAG 路径未匹配。
  • 500 内部错误：服务器异常兜底。
  • embedding_timeout：向量服务响应超时，记忆侧自动降级关键词通道。
  • vector_status_failed：向量状态查询失败。
  • invalidEmbeddingMode：embedding 模式非法。
  • rebuild recovery scan failed：RAG 重建恢复扫描失败。

排查步骤：

  1. 确认 Bearer Token 是否正确。
  2. 检查请求体是否为合法 JSON。
  3. 对于 RAG 导入，确认 type 是否在 text/file/url 中。
  4. 对于记忆写入，确认 action/type/content/importance 是否符合要求。
  5. 对于向量相关错误，检查 embedding-config 与 test-embedding 返回值。
  6. 查看进程日志中的 [Memory] route error、[RAG] route error、[RAG] rebuild recovery scan failed 等关键字。

结论 ​

记忆管理与 RAG 检索共同构成 AI 助手的核心知识能力：记忆用于短期对话上下文之外的长期事实与摘要，RAG 用于结构化知识库的语义检索。两者都强调：

  • 可扩展的嵌入提供者（本地/远端）。
  • 稳健的错误降级（向量失败不破坏关键词通道）。
  • 清晰的 API 契约（认证、CORS、JSON 响应、错误码）。
  • 可观测的状态（vector-status、rag/status、ingest/status）。

在实际使用中，建议：

  • 首次启用向量通道后调用 /api/memory/reindex 重建缓存。
  • 使用 /api/rag/test-embedding 验证远端向量服务连通性与维度。
  • 合理设置 topK 与 threshold，平衡召回率与精确率。
  • 定期使用 /api/memory/manage?action=compact 清理低价值记忆。
