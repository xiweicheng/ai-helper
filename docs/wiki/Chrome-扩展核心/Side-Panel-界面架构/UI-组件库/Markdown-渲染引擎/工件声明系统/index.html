引言 ​

本文件聚焦“工件（Artifacts）声明系统”，即 AI 助手在完成任务后，如何把 Agent 执行过程中产生的文件、目录以及 AI 显式声明的产物，统一提取、合并、校验并展示给用户的完整链路。该系统由两部分组成：

  • 静态工件提取：从任务执行日志中解析 agent_exec、agent_file、file_upload 等工具调用，推断写文件、创建目录、删除路径等操作。
  • AI 声明工件：从助手最终回答文本中解析形如 [[artifact:路径|可选说明]] 的标记，并与静态工件合并去重，补充说明信息。

该系统的实现位于侧边栏模块，核心逻辑集中在 src/side_panel/artifacts-manager.js，并在聊天消息渲染流程中被 src/side_panel/chat-manager.js 消费；背景进程中的 ReAct 执行循环则负责生成可供分析的 executionLog。

项目结构定位 ​

工件声明系统属于扩展端 MV3 Service Worker 架构下的侧边栏功能，不直接修改 Agent 源码，而是通过读取已持久化的任务执行日志和助手回复内容完成工件发现。

架构总览 ​

工件声明系统的数据流可以概括为三个阶段：

  1. 数据准备阶段

    • 背景进程执行 Agent 工具，产生结构化执行日志。
    • 聊天管理器将执行日志与助手回复文本注入到消息 DOM 的 data-* 属性中。

  2. 工件构建阶段

    • 聊天管理器调用静态提取函数，得到基础工件集合。
    • 若存在声明工件，则调用合并函数进行去重与说明补全。
    • 同步预过滤已删除工件，避免无效条目进入后续流程。

  3. 交互与校验阶段

    • 点击工件按钮时打开弹窗，渲染表格行。
    • 异步校验工件是否仍在工作目录内且真实存在。
    • 根据校验结果更新徽章计数、表格内容与空状态提示。

详细组件分析 ​

静态工件提取器 ​

静态工件提取是工件系统的核心引擎，负责从 executionLog 中识别三类来源：

  • agent_exec：解析 shell 命令链，识别写入、创建、复制、删除、脚本执行、heredoc 内联脚本等。
  • agent_file：处理显式的 write/delete 操作。
  • file_upload：处理上传到工作目录的文件。

其关键行为包括：

  • 按时间排序执行日志，保证“先创建后删除”的时序语义正确。
  • 维护 seenPaths 去重，同一路径只保留最后一次操作。
  • 维护 createdRoots 记录本任务创建的目录根，用于限制观察输出兜底解析的范围。
  • 维护 deletedPaths 记录删除操作，并在后处理阶段标记工件为已删除。
  • 对 ls -R、find 等列表输出做兜底解析，但仅在确有写操作或路径位于已创建根下时才采信。

AI 工件声明解析与合并 ​

AI 声明工件采用固定标记格式：

  • 基本语法：[[artifact:路径|可选说明]]
  • 变量引用路径会被丢弃，因为无法静态确定真实文件名。
  • 声明工件与静态工件按规范化路径去重；若命中已有静态工件，则优先补充说明字段。

合并策略要点：

  • 规范化路径时去除前导 ./，使 a.xlsx 与 ./a.xlsx 视为同一文件。
  • 若声明路径与静态绝对路径尾段一致，也视为同一文件，避免重复行。
  • 声明工件默认类型为 file，工具名为 declared，时间戳为空，状态为 unknown。

工件弹窗与交互 ​

工件弹窗提供以下交互能力：

  • 按文件名、类型、时间排序。
  • 双击文件名预览支持的文件。
  • 单击行或定位按钮定位到工作目录。
  • 复制文件名或按住 Ctrl/Cmd 复制绝对路径。
  • 单文件下载或目录 Zip 下载。
  • 异步校验后隐藏无效工件，全部无效时显示空状态。

弹窗的生命周期包括：

  • 打开时重置排序状态。
  • 渲染表头与表格行。
  • 绑定行事件与表头排序事件。
  • 异步校验后重新渲染或显示空状态。
  • ESC 关闭、遮罩挂载位置适配嵌入模式。

背景执行循环与 observation 的关系 ​

背景进程中的 ReAct 执行循环会生成包含 observation 字段的执行日志。工件管理器会利用该字段进行两类增强：

  • 从 agent_file 或 agent_exec 的观察输出中尝试解析真实路径。
  • 对 ls -R、find 等列表输出做兜底解析，反推可能的新建工件。

文档注释明确指出：日志中的 observation 会被产物提取逻辑用于解析路径。

性能与复杂度 ​

工件提取算法的时间复杂度主要受执行日志规模影响：

  • 排序：O(n log n)。
  • 主循环：O(n)，其中每条日志可能触发命令链拆分、正则匹配、路径展开、脚本内容分析等。
  • 列表输出兜底解析：对 observation 字符串做 token 化与规则过滤，近似 O(m)，m 为输出 token 数。
  • 后处理删除标记：O(k × d)，k 为工件数，d 为删除路径数。

空间复杂度方面：

  • seenPaths、scriptContentMap、deletedPaths、createdRoots 均随日志规模增长。
  • 大体积 observation 或长脚本内容会增加内存占用。

优化建议：

  • 对超大执行日志可考虑分页或增量构建工件。
  • 对频繁调用的 normalizePath、expandBraces 可引入缓存。
  • 对 Agent 离线场景保持降级策略，避免阻塞 UI。

故障排查指南 ​

工件按钮未出现 ​

可能原因：

  • 执行日志为空或格式异常。
  • 没有检测到写文件、创建目录或上传文件操作。
  • 所有工件均被判定为已删除、不在工作目录内或不存在。

排查步骤：

  1. 检查消息元素是否包含 dataset.executionLog。
  2. 确认 extractArtifactsFromExecutionLog 能返回非空列表。
  3. 检查 preFilterDeletedArtifacts 是否移除了全部工件。
  4. 检查 filterInvalidArtifacts 异步校验是否因 Agent 离线而失败。

工件数量与实际不符 ​

可能原因：

  • 声明工件与静态工件路径不一致导致重复或遗漏。
  • 相对路径与绝对路径未正确归一化。
  • 工作目录未知时，目录外工件未被过滤。
  • Agent 离线时，存在性检查失败，系统降级保留工件。

排查步骤：

  1. 检查 dataset.declaredArtifacts 是否正确序列化。
  2. 检查 mergeDeclaredArtifacts 的去重键计算。
  3. 检查工作目录根是否可通过 getWorkspaceRoot 获取。
  4. 检查 CHECK_FILES_EXIST 响应是否成功。

结论 ​

工件声明系统通过“静态分析 + AI 声明 + 异步校验”的三段式架构，实现了从 Agent 执行日志到用户可见工件展示的完整闭环。其设计重点在于：

  • 对 shell 命令链、脚本内容、列表输出进行多层次解析，提高工件发现覆盖率。
  • 通过时序把关与根目录约束，降低误报风险。
  • 通过声明工件机制，允许 AI 显式补充静态分析无法确定的工件信息。
  • 通过异步校验与降级策略，在 Agent 离线或文件变化时保持用户体验稳定。

对于开发者而言，扩展工件系统时应优先关注：

  • 新增工具调用类型时，补充对应的路径提取逻辑。
  • 新增声明格式时，同步更新解析与合并逻辑。
  • 变更路径解析规则时，确保相对路径、绝对路径、家目录、工作目录边界条件正确。
  • 变更 UI 行为时，确保事件绑定、弹窗生命周期与徽章计数保持一致。
