引言 ​

本文件面向“会话管理系统”，围绕 Chrome 扩展侧（Manifest V3，side panel + background）的会话生命周期、状态模型、多会话隔离、持久化、恢复机制、依赖关系与性能优化进行系统化说明。系统采用双进程架构：浏览器扩展端负责 UI、状态与本地存储；Agent 端提供 ReAct 执行循环、工具调用、长期记忆与 RAG 能力。文档以仓库中实际实现为依据，重点覆盖以下目标：

  • 会话创建、激活、切换、暂停与销毁流程
  • 会话状态模型：消息历史、上下文窗口、工具调用记录、元数据字段
  • 多会话隔离：内存隔离、存储分离、事件监听器管理
  • 持久化策略：IndexedDB 存储格式、自动保存触发条件、数据迁移逻辑
  • 恢复机制：断点续传、网络中断处理、进度同步
  • 会话间依赖：父子会话、任务分解、结果聚合
  • 性能优化：消息分页加载、内存清理、索引策略

项目结构 ​

会话相关代码主要分布在以下模块：

  • 存储层：src/storage/db.js（IndexedDB 封装）、src/storage/session-store.js（会话适配器）
  • 会话管理层：src/side_panel/session-manager.js（对外 API 兼容层）
  • 运行时状态：src/side_panel/state.js（全局状态与按会话隔离字段）
  • 聊天与流式输出：src/side_panel/chat-manager.js、src/side_panel/chat-streaming.js
  • 恢复机制：src/side_panel/chat-resume.js
  • 界面交互：src/side_panel/session-manager-ui.js、src/side_panel/index.js

核心组件 ​

  • 会话存储适配层（session-store.js）：封装 IndexedDB 操作，提供会话 CRUD、归档、复制/分叉、导入导出、滚动位置清理等能力，并维护活跃会话 ID。
  • IndexedDB 封装（db.js）：提供 Promise 化的数据库访问、事务重试、版本升级、对象存储定义、ReAct checkpoint 双写与 TTL 清理。
  • 会话管理 API（session-manager.js）：对外暴露与旧版一致的 API，同时维护“完成待查看”集合，桥接 UI 与存储层。
  • 全局状态（state.js）：集中管理当前活跃会话、消息历史、模型参数、工具开关、MCP 服务列表、按会话隔离的执行状态与取消映射。
  • 聊天管理器（chat-manager.js）：负责聊天历史加载、消息发送、流式输出、上下文压缩、RAG 注入、错误提示与 UI 联动。
  • 恢复模块（chat-resume.js）：提供“继续执行任务”对话框、checkpoint 验证、废弃 checkpoint 检测、resumeTask 恢复流程。
  • 会话 UI（session-manager-ui.js）：渲染会话标签、关闭/删除确认、重命名、排序、切换后 Agent 绑定恢复。

详细组件分析 ​

会话生命周期管理 ​

会话生命周期包括创建、激活、切换、暂停与销毁五个阶段。

  • 创建：通过 createSession() 生成唯一 ID、默认标题、模型参数、工具开关、时间戳、空消息历史，并写入 IndexedDB，同时设置为活跃会话。
  • 激活：首次打开时若无活跃会话，聊天管理器会自动创建默认会话并渲染标签栏。
  • 切换：switchToSession() 并发保存当前会话、读取目标会话、设置活跃 ID、恢复消息历史、上下文压缩记录、模型/温度/TopP、工具开关、Agent 绑定，并触发 UI 更新事件。
  • 暂停：后台任务进行中时，通过 pendingCallApiSessionIds 标记会话处于“生成中”，支持多会话并行；Service Worker 重启时通过 syncPendingSessionsToStorage() 持久化该集合，避免状态丢失。
  • 销毁：deleteStoreSession() 删除会话、清理 scrollPosition、ReAct checkpoint、收藏项，若删除的是活跃会话则就近激活相邻会话或清空活跃 ID。

会话状态模型 ​

会话状态模型由持久化字段与运行时字段共同构成：

  • 持久化字段（会话对象）：
    • id、title、model、useTools、enabledTools、agentId、temperature、topP
    • messageHistory（数组，含 role、content、executionLog、reflectionScore、wasRevised、htmlContent、messageId、timestamp、contextBubbles、resumable）
    • scrollPosition、createdAt、updatedAt、order、isGenerating、lastExecutionLog
    • forkMetadata（分叉来源与会话级分叉点 upToMessageId）
    • scheduledTaskId（定时任务宿主会话标识）
  • 运行时字段（state.js）：
    • activeSessionId、messageHistory、currentModel、temperature、topP、useTools、activeAgentId
    • sessionExecutionStatus、pendingCancelApiMap、pendingCallApiSessionIds、substituteLoadingIds
    • mcpClosedServers、customAgents、agentPlatform、bookmarks 等

上下文窗口与消息预算：

  • 上下文窗口由模型配置决定，可通过 getContextWindow() 获取；消息预算 = 上下文窗口 - 系统提示词 token - 输出预留 - 安全余量。
  • 自动压缩（autoCompaction）可压缩历史消息为摘要，并通过 activeCompaction 记录压缩点，随会话持久化。

工具调用记录：

  • executionLog 数组记录工具调用、反思评估、子任务计划与执行节点，用于 UI 展示与质量评估。

元数据字段：

  • forkMetadata 记录分叉来源与会话级截断点；scheduledTaskId 标识定时任务宿主会话；contextCompaction 记录会话级压缩状态。

多会话隔离机制 ​

系统通过以下机制保证多会话隔离：

  • 内存隔离：
    • pendingCallApiSessionIds 使用 Set 记录有后台任务的会话 ID，支持多会话并行。
    • pendingCancelApiMap 使用 Map 按 sessionId 隔离取消函数，防止多会话互相覆盖。
    • sessionExecutionStatus 使用 Map 按 sessionId 隔离执行状态。
    • 流式输出通过 createStreamingElementAccessor(sessionId) 按会话隔离 DOM 元素与累积内容。
  • 存储分离：
    • 每个会话在 IndexedDB 的 sessions store 中有独立记录，主键为 id。
    • 活跃会话 ID 单独存储在 activeSession store，key 固定为 'active'。
    • 归档会话、收藏、UI 原型、Token 统计、ReAct checkpoint、定时任务均独立存储。
  • 事件监听器管理：
    • 会话切换时触发 session-switched 自定义事件，通知 UI 更新标签栏与 Agent 选择器。
    • 生成状态变更触发 generating-state-changed 事件，驱动标签指示器刷新。
    • 会话缓存失效通过 session-cache-invalidate 事件通知 UI 重建 DOM。

会话持久化策略 ​

持久化策略基于 IndexedDB，并提供 chrome.storage.local 兜底：

  • 存储格式：
    • sessions store：会话对象，主键 id，索引 updatedAt。
    • activeSession store：单条记录 key='active'，值包含 sessionId。
    • archivedSessions store：归档会话，主键 id，索引 createdAt。
    • reactCheckpoints store：ReAct checkpoint，主键 sessionId，索引 updatedAt。
    • 其他：bookmarks、uiPrototypes、tokenStats、scheduledTasks。
  • 自动保存触发条件：
    • 每次切换会话前调用 saveCurrentSession()。
    • 消息发送后调用 saveChatHistory()。
    • 归档、复制、导入、重命名、排序等操作后持久化。
    • Service Worker 重启时通过 syncPendingSessionsToStorage() 恢复 pendingCallApiSessionIds。
  • 数据迁移逻辑：
    • ensureMigration() 检查 IndexedDB 是否有数据，无则从 chrome.storage.local 迁移 sessions 与 conversationSessions。
    • 迁移后清除旧的大数据 key（sessions、conversationSessions、chatHistory）。
    • cleanupOrphanScrollPositions() 清理已删除会话对应的 scrollPosition_* 残留键。

会话恢复机制 ​

恢复机制基于 ReAct checkpoint，支持断点续传、网络中断处理与进度同步：

  • 断点续传：
    • ReAct 循环定期保存 checkpoint 到 IndexedDB 与 chrome.storage.local（双写）。
    • 页面关闭/刷新后，_checkForAbandonedCheckpoint() 检测是否存在未清理的 checkpoint，自动添加“继续执行”提示卡片。
    • _verifyCheckpointAndHideButton() 异步验证 checkpoint 是否存在，不存在则移除按钮与 resumable 标记。
  • 网络中断处理：
    • resumeTask() 复用 callApi 的流式输出基础设施，通过 resumeFromCheckpoint 切换为发送 RESUME_REACT。
    • 捕获 SW 重启、用户停止、checkpoint 不存在等错误，分别显示友好提示并清理 resumable 标记。
  • 进度同步：
    • 恢复成功后，调用 _clearResumableFlagsForSession() 清除所有 resumable 标记，避免无效按钮。
    • 若已切换到其他会话，通过 appendMessageToSession() 将结果追加到原会话历史，并触发 session-cache-invalidate 事件重建 DOM。

会话间的依赖关系 ​

系统支持父子会话、任务分解与结果聚合：

  • 父子会话：
    • 通过 forkMetadata.sourceSessionId 记录分叉来源，支持会话级分叉（upToMessageId）与完整复制。
    • 定时任务通过 createScheduledSession() 创建专属宿主会话，标记 scheduledTaskId，便于识别与清理。
  • 任务分解：
    • ReAct 循环通过 subtask_plan 日志节点生成子任务清单，支持并行执行与节流。
    • 子任务状态分类（success/failed/partial）与过滤逻辑在 classifySubtaskOutcome() 与 applyNodeFilter() 中实现。
  • 结果聚合：
    • 子任务执行结果汇总为最终输出，支持部分完成时的橙色提示，避免误判为全部失败。
    • 恢复成功后，通过 markSessionCompleted() 标记会话完成待查看，用户切回后清除标记。

性能与优化 ​

会话管理系统的性能优化主要体现在以下几个方面：

  • 消息分页加载：
    • 聊天历史加载时优先渲染会话标签栏，再检查 checkpoint，避免 SW 往返阻塞 UI。
    • 历史恢复时统一绑定事件委托，避免重复绑定。
  • 内存清理：
    • 会话切换时清空已渲染的消息与上下文气泡，避免历史重载导致内容重复。
    • 流式输出通过 deleteStreamingState(sessionId) 清理 DOM 元素引用与累积内容。
    • 归档会话最多保留 20 条，超出时截断。
  • 索引策略：
    • IndexedDB 为 sessions、archivedSessions、reactCheckpoints、bookmarks、tokenStats 等 store 创建索引，提升查询性能。
    • 搜索消息时优先使用主键查询（sessionId），避免全量加载。
  • 并发优化：
    • 会话切换时并发保存当前会话与读取目标会话，减少等待时间。
    • 批量保存会话时使用单一事务，提升写入效率。

故障排查指南 ​

常见问题与排查方法：

  • 会话切换后状态不一致：
    • 检查 switchToSession() 是否正确保存当前会话并恢复目标会话状态。
    • 确认 state.activeSessionId 与 state.messageHistory 是否同步更新。
  • 后台任务状态丢失：
    • 检查 pendingCallApiSessionIds 是否在 SW 重启后通过 syncPendingSessionsToStorage() 恢复。
    • 确认 isGenerating 标记是否与 pendingCallApiSessionIds 一致。
  • 恢复功能不可用：
    • 检查 checkpoint 是否存在（GET_CHECKPOINT），是否被清理或过期。
    • 确认 _checkForAbandonedCheckpoint() 是否自动添加恢复提示卡片。
  • 持久化失败：
    • 检查 IndexedDB 连接是否正常，store 是否存在。
    • 确认 withStore() 的事务重试逻辑是否生效。

结论 ​

会话管理系统通过分层架构、多会话隔离、IndexedDB 持久化与 ReAct checkpoint 恢复机制，提供了完整的会话生命周期管理能力。系统在性能优化、错误处理与用户体验方面进行了细致设计，支持多会话并行、断点续传、任务分解与结果聚合。未来可进一步优化消息分页加载策略、增强内存清理机制，并扩展会话依赖关系的可视化展示。
