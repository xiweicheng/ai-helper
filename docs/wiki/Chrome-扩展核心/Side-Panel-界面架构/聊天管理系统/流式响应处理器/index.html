引言 ​

本文件面向“流式响应处理器”，聚焦本项目中基于 SSE（Server-Sent Events）的流式输出链路。该链路的核心目标是：在扩展端后台进程读取模型 API 的流式响应后，将文本增量、工具调用、推理内容、Token 用量等数据实时推送到侧面板，并在 UI 上实现思考过程、工具卡片、执行结果和最终消息的渐进式呈现。

需要特别区分两个概念：

  • 模型 API 的 SSE 流：由 StreamController 与 readSSEStream 负责解析 OpenAI 兼容格式的 data: 行，提取 choices.delta.content、tool_calls、finish_reason 与 usage。
  • 扩展内部的消息通道：通过 chrome.runtime.sendMessage 向侧面板发送 STREAM_START、STREAM_CHUNK、STREAM_TOOL_CALL、STREAM_DONE 等事件；这不是浏览器原生 EventSource，而是扩展进程间消息协议。

此外，项目中还存在 Agent 端心跳与健康检查逻辑，但它是针对本地代理进程的保活机制，并非模型 SSE 连接的心跳。文档会在相应章节明确区分这两者。

readSSEStream：ReadableStream 读取与空闲超时保护 ​

readSSEStream 负责从 fetchResponse.body.getReader() 中逐块读取二进制数据，解码为文本，按行拆分，再交给 StreamController.feedLine。其关键特性包括：

  • 立即调用 controller.sendStart()，让前端尽早显示“思考中”。
  • 使用 TextDecoder 进行流式解码。
  • 使用 Promise.race 同时监听 reader.read()、空闲超时和 abortSignal。
  • 空闲超时默认 120 秒，名称为 StreamIdleTimeout。
  • 遇到 AbortError 不发送 STREAM_DONE，避免残留消息污染后续任务。
  • 遇到空闲超时主动 reader.cancel()，然后调用 controller.finish() 并抛出异常。
  • 正常结束时调用 controller.finish()，返回 { status: 'done', ...result }。
  • 当检测到 finish_reason === 'tool_calls' 时提前返回 { status: 'tool_calls', ...result }，供 ReAct 循环继续执行工具。

chat-streaming.js：侧面板流式渲染 ​

侧面板负责把后台推送的事件转化为可交互的 UI。核心职责包括：

  • 创建流式消息容器，包含思考指示器、停止按钮、状态区域。

  • 重连流式元素，补充脱落期间缺失的内容。
  • 管理流式状态访问器，防止多会话并行串台。

SSE 连接与生命周期管理 ​

连接建立 ​

本项目没有使用浏览器原生 EventSource 来连接模型 API，而是使用 fetch 获取 Response.body，再通过 getReader() 获得 ReadableStream。readSSEStream 直接消费该流，因此：

  • 连接建立由 fetch 完成。
  • 流读取由 readSSEStream 管理。
  • 后端解析由 StreamController 完成。
  • 前端渲染由 chat-streaming.js 消费 STREAM_* 消息完成。

这种设计允许更细粒度的控制，例如自定义空闲超时、主动取消 reader、在工具调用中途退出流式读取。

心跳检测 ​

需要严格区分两类心跳：

类型目标实现位置是否 SSE 心跳
模型 SSE 空闲超时检测流式数据卡住stream-controller.js 中 STREAM_IDLE_TIMEOUT_MS不是传统 SSE 心跳，而是“无数据超时”保护
Agent 健康检查与心跳检测本地代理进程src/background/index.js 中 startAgentHealthCheck、performAgentHeartbeat不是模型 SSE 心跳，是扩展与 Agent 之间的保活

模型 SSE 空闲超时默认 120 秒，每次收到数据块都会重置计时器。如果持续无 SSE 事件，则抛出 StreamIdleTimeout。

Agent 心跳每 60 秒向活跃代理发送一次轻量 GET 请求，用于刷新代理端的认证时间，使其感知插件在线。

自动重连 ​

在当前代码中，模型 SSE 流本身没有内置自动重连逻辑。readSSEStream 在空闲超时或网络错误时会抛出异常，由上层 react-loop.js 捕获并记录错误。

不过，项目实现了“上下文超限自愈”：当 HTTP 400 且错误信息包含 context、token、too long 等特征时，会强制裁剪消息并重试本轮。这属于业务层重试，而不是底层 SSE 重连。

对于 Agent 端，健康检查和心跳主要用于保持代理进程在线感知，并不直接对模型 SSE 做断线重连。

优雅关闭 ​

优雅关闭的关键点如下：

  1. 用户点击“停止生成”时，ReAct 循环会通过 abortSignal 中断 reader.read()。
  2. readSSEStream 捕获 AbortError，不调用 controller.finish()，避免发送残留 STREAM_DONE。
  3. 空闲超时时，先 reader.cancel() 释放底层流，再调用 controller.finish()，最后抛出异常。
  4. 正常结束时，调用 controller.finish()，发送 STREAM_DONE，包含最终内容、推理内容、usage 和规范化后的 tool_calls。
  5. 侧面板在流结束后清理流式状态，并将思考指示器替换为思考结果。

增量更新算法 ​

文本流式渲染 ​

StreamController.feedLine 会累积 delta.content 到 fullContent，然后通过 sendChunk 节流发送 STREAM_CHUNK。侧面板的 updateStreamingMessage 接收完整累积内容，并使用 Markdown 渲染函数重新渲染当前轮次的思考内容。

关键点：

  • 增量来自模型 SSE，但前端渲染的是累积全文，而非仅追加最后一个 delta。
  • 思考过程中，思考指示器保持可见，首次出现内容时将“思考中”改为“输出中”。
  • 多轮 ReAct 会追加多个 thinking-content 块，每轮结束后插入“思考结果”徽章。
  • 滚动控制区分程序滚动和用户滚动，避免误判。

工具调用实时显示 ​

当模型返回 finish_reason === 'tool_calls' 时，StreamController 会：

  1. 规范化 toolCalls。
  2. 先 flush 剩余内容，确保思考内容先显示。
  3. 发送 STREAM_TOOL_CALL，携带累积的 toolCalls 和 fullContent。
  4. 返回 status: 'tool_calls'，让 ReAct 循环继续执行工具。

侧面板收到 STREAM_TOOL_CALL 后，会隐藏思考指示器，插入“思考结果”徽章，并为每个工具调用创建卡片。卡片包含工具名、参数摘要、执行中状态、终止按钮和展开/折叠能力。

流式数据解析与完整性校验 ​

JSON 流解析 ​

StreamController.feedLine 的处理顺序如下：

  1. 忽略空行和注释行。
  2. 提取 data: 前缀后的内容。
  3. 识别 [DONE]。
  4. 尝试 JSON.parse，失败则忽略该行。
  5. 优先提取 chunk.usage，即使后续 choices 为空。
  6. 取 choices[0]，不存在则忽略。
  7. 累积 reasoning_content。
  8. 累积 content。
  9. 累积 tool_calls。
  10. 根据 finish_reason 决定返回类型。

Line["SSE 行"] --> Prefix{"是否 data: 行？"}
Prefix --> |否| Ignore["忽略"]
Prefix --> |是| DoneCheck{"是否为 [DONE]？"}
DoneCheck --> |是| Done["返回 done"]
DoneCheck --> |否| Parse["JSON.parse"]
Parse --> Valid{"解析成功？"}
Valid --> |否| Ignore
Valid --> |是| Usage["提取 usage"]
Usage --> Choice{"是否存在 choices[0]？"}
Choice --> |否| Ignore
Choice --> |是| Delta["处理 delta"]
Delta --> Reasoning["累积 reasoning_content"]
Delta --> Content["累积 content"]
Delta --> Tools["累积 tool_calls"]
Tools --> Finish{"finish_reason？"}
Finish --> Stop["stop / length"]
Finish --> ToolCalls["tool_calls"]
Finish --> More["继续累积"]

数据完整性校验 ​

当前实现的完整性校验相对轻量：

  • 对无效 JSON 行直接忽略。
  • 对缺少 choices[0] 的 chunk 忽略。
  • 对 tool_calls 使用 normalizeToolCalls 过滤空洞和无效元素，并补齐缺失的 id。
  • 对 arguments 字段做防御性处理，兼容字符串和已解析对象。
  • 对 [DONE] 和 finish_reason 分别处理，避免丢失最后一个 chunk 的数据。

不足点：

  • 没有对 SSE 行的完整性做强校验，例如 data: 后必须是合法 JSON。
  • 没有对 choices 的结构做深度校验。
  • 没有对 tool_calls.index 的连续性做严格校验，只是容忍稀疏数组。
  • 没有对 usage 的字段做 schema 校验。

错误恢复机制 ​

网络中断检测 ​

网络中断可能表现为：

  • reader.read() 抛出异常。
  • fetch 返回非 OK 状态。
  • 长时间无数据触发空闲超时。

当前处理策略：

  • AbortError：视为用户取消，不发送 STREAM_DONE，直接抛出异常。
  • StreamIdleTimeout：主动 cancel reader，调用 controller.finish()，抛出带 idleMs 的错误。
  • 其他错误：记录日志，调用 controller.finish()，抛出异常。
  • ReAct 层区分用户取消、空闲超时和普通错误，并写入执行日志。

Cancel --> ThrowAborted["抛出 AbortError"]
Name --> |StreamIdleTimeout| CancelReader["reader.cancel()"]
CancelReader --> Finish["controller.finish()"]
Finish --> ThrowTimeout["抛出 StreamIdleTimeout"]
Name --> |其他| FinishOther["controller.finish()"]
FinishOther --> ThrowOther["抛出普通错误"]

断点续传 ​

当前代码中没有实现模型 SSE 的断点续传。原因包括：

  • 模型 SSE 通常是单向流，客户端无法像下载文件一样通过 Range 头续传。
  • 流式响应包含对话上下文，不能简单从某个字节偏移恢复。
  • 工具调用可能已经执行，盲目续传可能导致副作用重复。

项目提供的“恢复”能力更接近“会话级恢复”和“上下文自愈”：

  • 上下文超限自愈：400 错误时裁剪消息并重试。
  • 自动续跑：通过后台闹钟和通知机制提醒用户或自动恢复任务。
  • 流式元素重连：侧面板在 DOM 脱落后补回缺失内容，但这不是网络断点续传。

虚拟滚动 ​

当前代码中没有实现完整的虚拟滚动。主要优化集中在：

增量 DOM 更新 ​

流式渲染采用“累积全文 + 局部替换”的策略：

  • 每次 STREAM_CHUNK 都传入完整 fullContent。
  • updateStreamingMessage 查找当前轮的 thinking-content 并替换其 innerHTML。
  • 多轮 ReAct 会追加新的 thinking-content，而不是无限增长单个节点。
  • 工具卡片按需创建，支持展开/折叠减少初始渲染压力。

这种方式比纯追加 delta 更容易处理 Markdown 结构变化，但代价是每次都要重新渲染整段内容。对于超长回答，可考虑分块渲染或懒加载代码块。

结论 ​

本项目的流式响应处理器以 StreamController 为核心，结合 readSSEStream 的流式读取、空闲超时保护和工具调用检测，实现了从模型 SSE 到侧面板渲染的完整链路。其优势在于：

  • 支持 OpenAI 兼容格式的 SSE 流。
  • 支持文本增量、推理内容、工具调用和 Token 用量。
  • 支持节流渲染、工具卡片实时展示和多轮 ReAct。
  • 支持用户取消、空闲超时和优雅关闭。
  • 支持侧面板流式元素重连和状态同步。

需要注意的限制包括：

  • 模型 SSE 没有内置自动重连。
  • 没有传统意义上的断点续传。
  • 流式渲染使用累积全文替换，可能对超长消息造成性能压力。
  • 心跳机制区分模型 SSE 和 Agent 保活，不应混淆。

未来优化方向可包括：

  • 增加更严格的 SSE 数据校验。
  • 引入虚拟滚动优化长消息列表。
  • 对超长 Markdown 内容做分块或懒加载。
  • 增加流式连接监控指标，如首包延迟、增量间隔、错误率。
  • 在业务层实现更完善的会话恢复和工具调用幂等控制。
