引言 ​

本文面向本地代理服务 Agent（Node.js，包名 ai-helper-agent，版本 2.3.1）的服务器架构文档。Agent 作为 Chrome 扩展的本地代理端，提供 HTTP API、WebSocket 实时通道、文件系统访问、命令执行、技能系统、MCP 工具注册与调用、长期记忆与 RAG 检索等能力。服务采用原生 Node.js http 模块与 ws 实现，不使用 Express；路由、中间件、认证、日志、配置、生命周期管理均集中在单入口文件中，并通过多个子模块解耦业务领域。

需要特别注意：Agent 是独立进程，源码或运行时配置修改后必须重启进程，新接口和配置才会生效。

Agent 代码位于 agent/ 目录，入口为 src/server.js，通过 package.json 暴露 CLI 命令 ai-helper-agent 与别名 aha。核心职责划分如下：

核心组件 ​

  • HTTP 服务器：基于 Node.js http.createServer，所有路由在 handleRequest 中按路径分支处理，不依赖 Express。
  • WebSocket 服务器：基于 ws 的 WebSocketServer({ noServer: true })，通过 server.on('upgrade') 接管 WebSocket 升级。
  • 配置系统：以 ~/.ai-helper-agent/config.json 为持久化载体，带内存缓存、mtime 失效、写锁、字段校验、敏感字段加密落盘。
  • 日志系统：JSON Lines 格式，按天写入 ~/.ai-helper-agent/logs/agent-YYYY-MM-DD.log，支持控制台输出、类别标签、自动清理、分页查询。
  • 安全与认证：Bearer Token 认证、CORS 仅放行 chrome-extension:// 来源、路径白名单、命令分级检查、回收站机制。
  • 生命周期管理：启动时初始化搜索工具、RAG 探测、MCP/Skill 异步初始化；优雅关闭终止子进程、断开 WebSocket、关闭 HTTP/WebSocket 服务器、清理 PID 文件。

架构总览 ​

Agent 的服务架构可理解为“单进程多路由”模型：一个 HTTP 服务器承载 REST API，一个 WebSocket 服务器承载命令执行实时流；两者共享认证、配置、日志与安全策略。

详细组件分析 ​

HTTP 服务器与路由机制 ​

HTTP 服务器由 startServer 创建，使用原生 http.createServer，所有请求进入 handleRequest。该函数承担以下职责：

  • 解析 URL、设置国际化语言上下文。
  • 处理 CORS 预检与响应头。
  • 区分无需认证接口与需认证接口。
  • 按 pathname 分发到具体业务逻辑。
  • 统一 JSON 响应封装。

关键路由分组如下：

分组典型端点行为
无认证/api/pair、/api/status配对码生成、平台状态与健康检查
控制面/api/shutdown、/api/agent/restart、/api/agent/update本机免认证关闭、远程需认证；重启与更新带冷却与防重入
文件操作/api/fs/read、/api/fs/write、/api/fs/list、/api/fs/download-stream路径白名单校验、大小限制、脚本权限剥离、ZIP 打包、流式传输
命令执行/api/exec、/api/exec/stop、/api/exec/detach命令安全检查、同步/异步模式、返回 WebSocket 地址
技能系统/api/skill/run、/api/skill/import、/api/skill/save-markdown导入、启用、运行、Markdown 管理

中间件处理流程 ​

Agent 没有传统意义上的 Express 中间件栈，而是通过 handleRequest 中的顺序判断模拟中间件效果：

  1. 国际化中间件：根据 Accept-Language 设置各子模块语言。
  2. CORS 中间件：仅放行 chrome-extension:// 来源，OPTIONS 预检直接返回。
  3. 配置刷新中间件：每次请求重新加载配置，避免 workdir 切换后快照过期。
  4. 认证中间件：除少数无认证接口外，其余均需 Bearer Token。
  5. 业务路由中间件：按路径分发给文件、命令、技能、MCP、RAG、记忆等模块。
  6. 错误兜底中间件：顶层 try/catch 捕获未处理异常，返回 500。

错误处理策略 ​

错误处理分为三层：

层级处理方式
请求级parseBody、parseMultipartBody 对超大 body、非法 JSON、非法 multipart 返回 400
路由级每个业务分支 catch 异常并记录日志，返回结构化 {success,error}
全局级handleRequest 外层 catch 返回 500；uncaughtException、unhandledRejection 监听记录但不退出进程

此外，端口占用错误会直接退出进程，避免半开服务。

WebSocket 通信实现 ​

WebSocket 用于命令执行的实时数据推送。核心流程：

  1. HTTP 端点 /api/exec 返回 wsUrl。
  2. 客户端连接 /ws/exec/{execId}，优先使用 Authorization: Bearer，回退到 ?token=。
  3. 服务端验证 token，失败直接 403。
  4. 将 WebSocket 加入执行器客户端列表。
  5. 心跳检测：每 30 秒 ping，未 pong 则 terminate。
  6. 客户端断开时移除连接，并按受管/旧语义处理超时。

服务生命周期管理 ​

生命周期包括启动、运行、关闭三个阶段：

  • 启动阶段：

    • 加载配置，开启终端日志输出。
    • 异步初始化搜索工具与 RAG 可用性检测。
    • 创建 HTTP 服务器与 WebSocket 服务器。
    • 启动配对码轮换、回收站定期清理。
    • 异步初始化 MCP 与 Skill 注册表，并启动 Skill 目录监听。

  • 运行阶段：

    • 处理 HTTP 请求与 WebSocket 升级。
    • 维护活跃 socket 集合用于优雅关闭。
    • 监控进程信号 SIGINT/SIGTERM。

  • 关闭阶段：

    • 停止配对码轮换与周期任务。
    • 中止 RAG 安装并回收 npm 进程树。
    • 终止所有运行中的命令进程。
    • 关闭 MCP 连接。
    • 强制断开所有 WebSocket 客户端。
    • 销毁活跃 HTTP socket，避免 server.close() 挂起。
    • 等待 server 与 wss 关闭，清理 PID 文件，退出进程。
    • 若 10 秒内未完成，强制退出防止卡死。

配置系统设计 ​

配置系统以 ~/.ai-helper-agent/config.json 为核心，设计要点如下：

  • 默认值合并：DEFAULTS 定义端口、主机、工作目录、允许路径、RAG 策略、记忆 embedding 等，用户配置覆盖默认值。
  • 内存缓存：loadConfig 使用 mtime 判断是否重新读取磁盘，减少 IO。
  • 写锁互斥：withWriteLock 保证并发写不会互相覆盖。
  • 敏感字段加密：memoryEmbedding.apiKey 与 pairing token 落盘前加密，内存中保持明文。
  • 自动白名单：skills 目录与工作目录自动加入 allowedPaths。
  • 字段校验：updateConfigField 仅允许合法 key，否则抛出国际化错误。

环境变量方面，当前配置模块未直接读取环境变量；但日志模块支持 AI_HELPER_LANG 设置日志语言。Agent 启动参数与 CLI 行为由 bin/agent.js 与 package.json scripts 驱动。

性能监控、日志记录、健康检查与调试工具 ​

  • 健康检查：

    • /api/status：返回版本、平台、架构、Node 版本、搜索工具可用性与 RAG 可用性。
    • /api/status/detail：需认证，返回内存使用、运行时长、CPU 时间、工作目录、允许路径、文件限制、运行进程等。
    • /api/heartbeat：需认证，仅刷新在线状态。

  • 性能监控：

    • 通过 /api/status/detail 获取 memoryUsedMB、memoryTotalMB、memoryRssMB、uptimeSeconds、cpuUser、cpuSystem。
    • 文件下载支持流式传输，避免一次性读入内存导致 OOM。
    • ZIP 打包使用临时文件并在完成后删除。

  • 日志记录：

    • 分类日志：auth、fs、exec、security、system。
    • 控制台输出开关由 setConsoleOutput(true) 启用。
    • 日志文件按日轮转，保留最多 30 个文件，单个文件超过 10MB 会被清理。

部署指南 ​

Agent 的官方安装渠道是 GitHub Releases 自动构建产物，不建议手动 clone 源码构建。部署时需关注以下方面：

  • Docker 容器化：

    • 基础镜像需满足 Node >= 18。
    • 暴露端口 18910（可通过配置修改）。
    • 挂载 ~/.ai-helper-agent 目录以持久化配置、workspace、memory、logs。
    • 注意容器内用户权限与宿主目录映射。

  • 环境变量设置：

    • AI_HELPER_LANG：设置日志语言（zh/en），默认检测系统语言。
    • 其他运行时参数通过配置文件 config.json 设置，如 port、host、workdir、allowedPaths、commandTimeout、fileMaxSize。

  • 端口配置：

    • 默认端口 18910，可在配置中修改。
    • 端口占用时会退出进程，避免半开服务。

  • 防火墙规则：

    • 建议仅开放 127.0.0.1:18910，避免暴露在公网。
    • 若需远程访问，应通过反向代理或 SSH 隧道，并确保 Bearer Token 安全。

  • 进程监控与自动重启：

    • 支持 /api/agent/restart 与 /api/agent/update，内部使用两阶段 spawn 重启包装器。
    • 更新失败不重启，保持老进程运行并提示用户手动执行。
    • 优雅关闭带 10 秒超时保护，防止进程卡死。

性能与容量特性 ​

  • 请求体限制：JSON body 最大 200MB，multipart 上传同样限制。
  • 文件读取限制：默认 50MB，可通过 fileMaxSize 调整。
  • 流式上传：/api/fs/upload-stream 支持原始二进制流，避免 base64 膨胀。
  • 流式下载：/api/fs/download-stream 使用 createReadStream 或分块写入，避免内存峰值。
  • ZIP 打包：临时文件写入 tmpdir，完成后删除，避免长期占用磁盘。
  • 日志清理：保留最近 30 个日志文件，单个文件超 10MB 清理，间隔 60 秒。
  • WebSocket 心跳：30 秒 ping，检测半开连接，防止僵尸连接占用资源。

故障排查指南 ​

常见问题与定位方法：

问题排查步骤
端口被占用查看启动日志，确认 EADDRINUSE 错误；检查是否有旧进程残留
无法连接 WebSocket检查 Token 是否正确，浏览器 WebSocket 不支持自定义 Header，需使用 ?token=
文件操作被拒绝检查 allowedPaths 是否包含目标路径，确认路径白名单校验
命令执行被拒绝查看命令安全检查级别，deny 直接拒绝，confirm 需前端确认
RAG 不可用调用 /api/rag/detect 查看探测结果，必要时执行 /api/rag/install
日志过多使用 /api/logs/query 查询最近 7 天日志，按类别过滤
进程卡住不退出检查优雅关闭是否触发，确认 10 秒超时是否生效

结论 ​

Agent 本地代理服务采用单进程多路由架构，以原生 http 与 ws 实现 HTTP 与 WebSocket 服务，通过统一请求处理器实现路由、认证、日志、配置与安全策略。其优势在于轻量、可控、易于调试；风险在于单进程阻塞与长驻进程模块缓存。部署时应严格限制网络暴露范围，合理配置端口与白名单，并利用健康检查、日志查询与优雅关闭机制保障稳定性。对于 Chrome 扩展侧，需注意 MV3 Service Worker 生命周期约束，确保保活与消息传递正确。
