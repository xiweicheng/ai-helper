引言 ​

本系统为 AI Helper 扩展的“文档图像识别”能力，目标是在用户上传 Word、PDF、Excel 等文档后，把文档内嵌图片转述为文本送入主模型对话；同时提供 read_document_image（现泛化为 read_image）工具，让 Agent 按需深读某张图。其关键设计是：主模型始终消费纯文本，视觉模型仅在插件端调用；Agent 端只负责 docx 抽图落盘和按需提供下载，不解析 PDF，也不接触任何模型调用。

该功能由规划与设计文档确认，并在扩展侧与代理侧分别实现：

  • 扩展侧：浏览器端抽取 docx/pdf/xlsx 图片、压缩、视觉转述、清单块生成、session 级快照中转。
  • 代理侧：基于 Node ESM 的最小 ZIP 读取器 + docx 图片提取 + /api/documents/extract-images 接口。
  • 工具层：background 执行 read_image，从 _docImageSnapshot 取图并调用视觉 API。

详细组件分析 ​

浏览器端文档图片抽取与视觉转述 ​

src/side_panel/doc-images.js 是扩展侧的核心模块，承担三类文档的图片抽取与视觉链路。

设计要点 ​

  • 开关统一复用 state.enableImageInput，不新增配置项。
  • 尺寸解析算法与 Agent 端 image-extractor.js 同步，避免两端编号不一致。
  • docx 使用 JSZip 解析 word/media/*，按 document.xml 中 r:embed 出现顺序编号。
  • xlsx 解析 workbook→rels→sheet→drawing→media，记录 sheet 名与单元格坐标。
  • pdf 在浏览器端用 pdfjs-dist，优先抓位图，无位图且文本稀少时整页渲染作为扫描件兜底。
  • 单图压缩采用 5 轮降级：先降 quality，再缩尺寸，仍超则放弃实体但保留清单元信息。
  • 视觉配置走 imageApiBase/imageApiKey/imageModelName，留空回落基础模型配置。

关键函数说明 ​

  • extractDocxImagesFromFile(file, opts)：浏览器端 docx 抠图，返回 images、truncated、skipped。
  • extractXlsxImagesFromFile(file, opts)：浏览器端 xlsx 浮动图片抠图，带 sheet 与 cell 定位。
  • extractPdfImagesFromFile(file, opts, deps)：浏览器端 pdf 抠图，支持位图去重与扫描页渲染。
  • compressForVision(dataUrl, deps)：将 dataUrl 压缩到视觉上限，失败返回 null。
  • describeImages(images, count, onEach)：并发调用视觉模型，返回 index→description 映射。
  • buildImageBlock(fileEntry, fileName)：拼装消息内联图片清单块。
  • saveDocImageSnapshot(sessionId, attachedFiles)：写入 session 级图片快照，按预算淘汰旧会话。

代理端 ZIP 读取器与 docx 图片提取 ​

代理端不引入 jszip，而是通过 node:zlib 实现最小 ZIP 读取器，仅支持 stored 与 deflate。

docx 提取流程 ​

  • 读取 word/document.xml 与 word/_rels/document.xml.rels。
  • 建立 rId→media 路径映射。
  • 按 r:embed 出现顺序收集唯一 media 路径。
  • 对 PNG/JPEG/GIF/BMP/WebP 进行头部尺寸解析，超过单图字节上限跳过。
  • 返回 images、truncated、skipped。

内置工具 read_image（原 read_document_image） ​

工具定义与执行逻辑位于 background 工具体系，测试用例明确其行为契约。

工具行为 ​

  • 参数二选一：{ file, image } 或 { path }。
  • 本地来源：从 _docImageSnapshot 中读取 dataUrl。
  • Agent 来源：通过 local-agent-client.downloadFile(path) 拉取 base64。
  • 安全校验：magic bytes 与单图体积上限必须通过。
  • 视觉调用：复用现有视觉配置链路与压缩逻辑。
  • 错误文案：包含文件名、可用附件、序号越界、缓存失效、Agent 离线、视觉未配置等。

性能与资源控制 ​

系统在多个环节设置了阈值与降级策略，防止大文档与大图拖垮浏览器或外部视觉服务。

控制点阈值或策略目的
单文档图片数量MAX_IMAGES = 20限制单文档抠图上限，超出记 truncated
单图原始字节MAX_RAW_BYTES = 5MB跳过过大图片，避免内存爆炸
单图视觉上限MAX_IMAGE_BYTES = 200KB压缩后送视觉模型，降低带宽与 Token
视觉转述并发前 DESCRIBE_LIMIT = 2 张并发缩短最坏等待时间
视觉请求超时60s AbortController防止外部 API 挂起
快照预算SNAPSHOT_BUDGET = 4MB淘汰旧会话 dataUrl，保当前会话
Agent 文件上限EXTRACT_MAX_FILE_BYTES = 50MB拒绝超大 docx
PDF 扫描页阈值SCANNED_PAGE_TEXT_THRESHOLD = 50文本稀少才整页渲染，减少无效渲染

结论 ​

文档图像识别系统以“浏览器端抽取 + Agent 端落盘 + background 工具深读”的分层架构实现，既满足主模型纯文本消费约束，又覆盖 docx、xlsx、pdf 三类常见办公文档。其关键保障包括：

  • 双端同步的 docx 编号算法与 PNG/JPEG 尺寸解析。
  • 浏览器端 pdf.js 统一处理，避免 Agent 端 canvas 依赖问题。
  • 多层阈值控制：图片数量、原始大小、视觉大小、快照预算、Agent 文件大小。
  • 工具层严格的安全校验：magic bytes、体积上限、参数二选一、视觉配置前置。
  • 完善的测试覆盖：浏览器端抽取单测与工具行为单测共同保证回归稳定性。

对于维护者而言，修改 docx 编号或尺寸解析需同时更新扩展侧与代理侧；修改视觉配置或工具参数需同步更新测试用例；Agent 端源码变更后必须重启进程，新接口才生效。
