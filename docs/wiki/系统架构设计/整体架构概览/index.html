引言 ​

本文件面向 AI Helper 系统的整体架构，重点解释双进程设计：**Chrome 扩展端（Manifest V3 Service Worker，版本 2.3.1）与独立 Node.js Agent 服务（版本 2.3.1）**的职责分离、协作方式、安全边界、保活机制、进程管理以及版本同步策略。

该架构的核心决策是：

  • 把浏览器上下文中的 UI 编排、工具调度、会话状态和页面交互放在 Chrome 扩展的 MV3 Service Worker 中；
  • 把本地文件系统访问、系统命令执行、长期记忆、RAG 索引、MCP 工具注册等需要操作系统权限或较重计算能力的逻辑交给独立 Agent 进程；
  • 两端通过本地 HTTP/WebSocket 接口通信，并使用 Bearer Token + Origin 白名单做基础隔离；
  • 版本号在扩展包与 Agent npm 包中保持一致，由 GitHub Actions Release 工作流统一构建和发布。

项目结构 ​

仓库采用“扩展根目录 + agent 子目录”的双工程结构：

  • 扩展根目录包含 Manifest、Vite 构建配置、background Service Worker、side panel、options、content script、shared 共享模块、测试脚本；
  • agent 子目录是一个独立的 Node.js npm 包，提供 ai-helper-agent CLI、HTTP+WebSocket 服务器、文件与命令执行、MCP、Skill、Memory/RAG 等能力；
  • .github/workflows/release.yml 负责构建扩展产物并生成 GitHub/Gitee Release。

架构总览 ​

AI Helper 的整体运行边界可以划分为四层：

  1. 用户界面层：Chrome 扩展 Action、Side Panel、Options 页面、Content Script 注入的页面工具。
  2. 扩展后台服务层：MV3 Service Worker，负责会话、工具调度、UI 状态、保活、通知、自动恢复。
  3. Agent 服务层：Node.js 进程，暴露本地 HTTP/WebSocket API，提供文件、命令、记忆、RAG、MCP、Skill 能力。
  4. 外部系统与 API 层：操作系统文件系统、Shell、模型提供商、MCP Server、RAG 向量存储、npm 源。

详细组件分析 ​

Chrome 扩展端：MV3 Service Worker 生命周期与保活 ​

MV3 Service Worker 不是常驻进程：当没有活跃任务时，Chrome 可能终止它；当被唤醒后，需要重建定时任务、恢复面板状态、清理过期 checkpoint。

关键约束与实现：

  • Service Worker 入口为 src/background/index.js，由 manifest 声明。
  • 启动时重建闹钟、迁移旧格式 Agent 配置、清理过期 ReAct checkpoint。
  • 通过 side panel 建立的 chrome.runtime.connect 长连接作为保活手段，防止 API 调用期间 SW 被判定空闲。
  • keepalive 端口按 sessionId 注册，支持重连检测、实例身份上报、SW 重启检测、面板断开延迟复核。
  • 侧边栏打开/关闭、全局/标签页绑定模式、Tab 分组、快捷键 toggle 都做了手势上下文保护。

Agent 服务：进程管理与运行时约束 ​

Agent 服务是一个独立 Node.js 进程，默认监听本地地址，对外暴露 HTTP 和 WebSocket 接口。

进程管理要点：

  • CLI 入口 agent/bin/agent.js 支持前台和后台模式。
  • 后台模式使用 spawn 拉起真实服务进程，写入 PID 文件，并通过轮询 /api/status 健康检查。
  • stop/restart 会先尝试优雅关闭，再回退到 SIGTERM/taskkill。
  • _restart-helper 是两阶段重启包装器：等待旧进程退出、端口释放，再启动新进程。
  • 服务端 /api/shutdown 写 .stopped 标记阻止 autostart 自动拉起。
  • 服务端 /api/agent/update 可触发 npm install -g ai-helper-agent@latest，失败不重启，成功则两阶段重启。

扩展端与 Agent 端的通信契约 ​

扩展端通过 local-agent-client.js 封装所有 Agent 接口，包括：

  • 配对与会话：/api/pair、/api/status、/api/status/detail
  • 文件系统：读、写、列表、删除、搜索、上传、下载
  • 命令执行：异步执行、等待结果、停止、detach
  • MCP：工具列表、调用、Server 管理
  • RAG：知识库集合、检索、文档处理

认证与安全：

  • 需认证的请求携带 Authorization: Bearer <token>。
  • Agent 服务端对非 /api/pair、/api/status 等公开接口强制校验 token。
  • CORS 仅放行 chrome-extension:// 来源，避免恶意网页跨域读取响应。
  • 文件路径、命令执行、上传大小、body 大小均有安全检查。

安全隔离机制 ​

系统的安全边界体现在多个层面：

  1. 浏览器扩展边界：Manifest 声明最小权限，Content Security Policy 限制脚本来源。
  2. CORS 白名单：Agent 服务端只允许 chrome-extension:// 来源跨域读取响应。
  3. Token 认证：除配对和健康检查外，所有敏感接口要求 Bearer Token。
  4. 路径与命令校验：Agent 端使用 checkPath、checkCommand 等安全函数。
  5. 文件大小与 body 限制：JSON body 最大 200MB，上传流式接口也有上限。
  6. 进程隔离：命令执行通过子进程，Agent 提供 kill、detach、超时控制。
  7. 更新互斥：Agent 更新与 RAG 依赖安装互斥，避免并发写 node_modules。

性能与可靠性特征 ​

  • Service Worker 保活：通过 side panel 长连接维持 SW 存活，避免频繁重建导致会话丢失。
  • 自动续跑：基于 ReAct checkpoint 和 chrome.alarms，SW 被回收后可自动恢复未完成任务。
  • 消息截断：chrome.runtime.sendMessage 有 64MiB 限制，大日志会被截断但保留子任务计划条目。
  • Agent 健康检查：CLI 启动后台服务后轮询 /api/status，确保服务真正就绪。
  • 更新互斥：Agent 更新与 RAG 安装互斥，避免并发破坏依赖。
  • 超时控制：HTTP 请求、WebSocket、命令执行、npm 安装均有超时保护。
  • 主题性能：CSS Token 在 :root 定义一次，暗色覆盖按需切换，减少重复样式计算。

故障排查指南 ​

常见故障点与建议：

  1. Service Worker 被终止：检查 side panel 是否仍保持 keepalive 连接；查看控制台是否有 SW_RESTARTED 或 checkpoint 恢复日志。
  2. Agent 未配对：确认扩展设置中已完成配对，且 Agent 服务正在运行；检查 /api/status 是否可达。
  3. CORS 拦截：确认请求来源是 chrome-extension://，不要从普通网页直接访问 Agent 接口。
  4. Token 无效：检查扩展存储中的 pairedAgents 是否包含有效 token；必要时重新配对。
  5. Agent 更新失败：查看 npm 安装输出；若失败，Agent 不会重启，应手动执行更新命令。
  6. RAG 依赖缺失：Agent 启动时会检测 RAG 可用性，失败时可能自动恢复依赖；若仍不可用，检查 Node 版本和网络源。
  7. 主题颜色异常：确认 data-theme 属性是否正确设置，避免硬编码色值，优先使用 CSS Token。

结论 ​

AI Helper 的双进程架构将浏览器上下文中的交互与系统级能力解耦：

  • Chrome 扩展端负责用户体验、会话编排、工具调度和安全边界；
  • Agent 端负责本地资源访问、命令执行、知识检索和可扩展工具生态；
  • 两端通过标准化 HTTP/WebSocket 接口协作，配合 Token 认证和 CORS 白名单保障安全；
  • Service Worker 的生命周期约束通过 keepalive、checkpoint、闹钟自动续跑缓解；
  • Agent 进程通过 CLI、健康检查、两阶段重启、更新互斥提升可靠性；
  • 版本同步由 GitHub Actions Release 工作流统一管理，扩展与 Agent 版本号保持一致。
