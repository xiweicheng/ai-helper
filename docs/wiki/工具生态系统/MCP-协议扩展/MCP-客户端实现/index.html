引言 ​

本文面向 MCP（Model Context Protocol）客户端实现，聚焦 Agent 端如何作为 MCP 客户端接入外部工具服务器。文档覆盖以下目标：

  • 连接建立过程与四种传输协议差异：stdio、SSE、Streamable HTTP、WebSocket。
  • 消息序列化与反序列化机制，以及工具自动发现流程。
  • 远程工具调用完整链路：参数校验、请求构建、响应处理、错误处理与重试策略。
  • 连接池管理、超时控制、资源清理策略。
  • 客户端配置项、连接参数调优与故障恢复方案。
  • 实际连接示例与调试技巧。

本项目采用双进程架构：Chrome 扩展端通过本地 HTTP/WebSocket 调用 Agent；Agent 再作为 MCP 客户端连接第三方 MCP Server。MCP 客户端相关逻辑集中在 agent/src/mcp 目录下，由 server.js 暴露 REST API 供扩展端调用。

项目结构 ​

MCP 客户端实现主要位于 Agent 端的 agent/src/mcp 目录，包含三个核心文件：

  • client.js：封装单个 MCP 客户端实例，负责传输层选择、连接、工具列表获取和工具调用。
  • registry.js：维护已连接的 MCP 客户端映射表，提供批量初始化、状态查询、工具扁平化、单服务连接/断开、全局关闭等能力。
  • mcp-config.js：持久化 MCP Server 配置，提供带缓存的加载、写入锁、增删改查接口。

Agent 主服务 server.js 将 MCP 管理能力暴露为 REST API，例如添加/删除/启用/禁用 MCP Server、连接/断开、查询工具列表、调用工具等。

详细组件分析 ​

McpClient：单个 MCP 客户端实现 ​

McpClient 是 MCP 客户端的核心类，封装了传输层选择、连接、工具发现、工具调用和资源释放。

传输层选择 ​

_createTransport() 根据 serverConfig.transport 创建对应传输实例：

  • stdio：默认值，需要 command、可选 args、env、cwd。
  • sse：需要 url，支持通过 headers 注入请求头。
  • streamableHttp：需要 url，支持通过 headers 注入请求头。
  • websocket：需要 url。

如果缺少必要字段，会抛出国际化错误信息，例如“SSE 传输需要提供 url”“stdio 传输需要提供 command”。

连接与工具发现 ​

connect() 执行以下步骤：

  1. 若已连接则直接返回成功。
  2. 创建传输层实例。
  3. 创建 SDK 客户端实例，名称固定为 ai-helper-agent，版本固定为 1.3.4。
  4. 调用 SDK 的 connect 完成握手。
  5. 读取服务器版本和能力。
  6. 调用 listTools 获取工具列表并缓存到 this.tools。
  7. 设置 connected = true，返回连接结果。

连接失败时会调用 disconnect() 清理资源，并返回包含错误信息的对象。

工具调用 ​

callTool() 的流程：

  1. 检查是否已连接，未连接则返回“MCP Server 未连接”错误。
  2. 调用 SDK 的 callTool，传入工具名和参数。
  3. 如果返回结果中包含 error，转换为失败响应。
  4. 否则从 result.content 中提取 type === 'text' 的内容，拼接为文本。
  5. 返回 { success, content, raw }。
  6. 捕获异常后返回国际化错误信息。

当前实现没有显式重试逻辑，但上层 Background 侧对工具调用结果有重试机制。

flowchart TD

Connected --> |否| ReturnNotConnected["返回未连接错误"]
Connected --> |是| CallSdk["调用 SDK callTool"]
CallSdk --> HasError{"返回结果是否包含 error"}
HasError --> |是| ReturnError["返回失败错误"]
HasError --> |否| ExtractText["提取 text 类型内容"]
ExtractText --> JoinText["拼接为字符串"]
JoinText --> ReturnSuccess["返回成功结果"]
CallSdk --> CatchErr["捕获异常"]
CatchErr --> ReturnCallError["返回调用异常错误"]

连接状态与资源清理 ​

disconnect() 会：

  • 设置 connected = false。
  • 清空 tools。
  • 尝试关闭 SDK 客户端。
  • 尝试关闭传输层。
  • 将引用置空。

getStatus() 返回当前服务的 ID、名称、连接状态、工具数量和服务器信息。

registry.js：MCP 工具注册表 ​

registry.js 维护一个 Map<serverId, McpClient>，提供多服务管理、工具扁平化和统一调用入口。

启动时初始化 ​

initializeMcpRegistry() 会：

  1. 加载 MCP 配置。
  2. 遍历所有启用的 server。
  3. 为每个 server 创建 McpClient 并连接。
  4. 记录成功连接数和失败列表。
  5. 输出日志提示连接情况。

工具列表获取 ​

getMcpTools() 会：

  1. 遍历所有已连接 client。
  2. 过滤掉未连接或指定 serverId 不匹配的服务。
  3. 将每个工具的 name、description、inputSchema 扁平化为统一结构。
  4. 返回 { success, tools }。

工具调用 ​

callMcpTool() 会：

  1. 查找 serverId 对应的 client。
  2. 检查 client 是否存在且已连接。
  3. 调用底层 client.callTool()。
  4. 返回调用结果。

连接管理 ​

  • connectMcpServer()：先断开已有连接，再新建 client 并连接。
  • disconnectMcpServer()：断开指定服务并从 Map 移除。
  • shutdownMcpRegistry()：Agent 关闭时统一断开所有连接并清空 Map。

mcp-config.js：MCP 配置管理 ​

该模块负责 MCP Server 配置的持久化与内存缓存。

配置路径与缓存 ​

  • 配置文件路径：用户目录下的 .ai-helper-agent/mcp_servers.json。
  • 内存缓存：configCache 和 configCacheMtime，避免重复解析。
  • 写入互斥锁：writeLock 保证并发写安全。

主要接口 ​

  • loadMcpConfig()：带 mtime 检测的加载函数，首次不存在时创建默认空配置。
  • saveMcpConfig()：加锁写入并更新缓存。
  • addMcpServer()：新增或更新 server。
  • removeMcpServer()：按 id 删除。
  • toggleMcpServer()：切换 enabled 状态。

server.js：MCP REST API 路由 ​

server.js 将 MCP 管理能力暴露为 HTTP API，关键路由如下：

路由方法功能参数校验
/api/mcp/serversPOST添加 MCP Server校验 id、http 需要 url、stdio 需要 command、stdio 命令安全检查
/api/mcp/serversDELETE删除 MCP Server校验 id
/api/mcp/servers/connectPOST连接指定 MCP Server校验 id
/api/mcp/servers/disconnectPOST断开指定 MCP Server校验 id
/api/mcp/servers/togglePOST启用/禁用 MCP Server校验 id 和 enabled；禁用时先断开连接
/api/mcp/callPOST调用 MCP 工具校验 serverId 和 toolName
/api/mcp/serversGET获取所有 MCP Server 状态无参数
/api/mcp/toolsGET获取所有 MCP 工具可选 serverId

其中，stdio 传输会对 command + args 进行安全校验，防止 MCP 成为命令管控后门。

性能与资源管理 ​

连接池管理 ​

当前实现不是传统意义上的连接池，而是“注册表 + 单例 per server”模式：

  • 每个启用的 MCP Server 对应一个 McpClient 实例。
  • registry.js 中的 clients Map 充当轻量级连接池。
  • 重启或手动重连时，会先断开旧连接再创建新实例。

这种设计适合 MCP Server 数量较少、连接数可控的场景。

超时控制 ​

  • McpClient 本身没有显式超时配置。
  • 超时控制主要由 SDK 和传输层实现决定。
  • Agent 层的通用请求超时逻辑不在 MCP 客户端内部体现。

资源清理策略 ​

  • disconnect() 会关闭 SDK 客户端和传输层。
  • shutdownMcpRegistry() 会在 Agent 关闭时统一清理所有连接。
  • 配置写入使用互斥锁，避免并发写导致文件损坏。

工具发现与缓存 ​

  • 工具列表在连接成功后立即拉取并缓存到 client.tools。
  • Background 侧对 MCP 工具列表有 30 秒缓存，减少频繁网络请求。

配置选项与连接参数调优 ​

MCP Server 配置字段 ​

字段类型必填条件说明
idstring所有传输服务唯一标识
namestring可选显示名称，默认为 id
transportstring可选传输类型：stdio、sse、streamableHttp、websocket
urlstringhttp 类传输必填SSE、Streamable HTTP、WebSocket 需要 URL
commandstringstdio 传输必填本地子进程命令
argsarraystdio 传输可选子进程参数数组
envobjectstdio 传输可选子进程环境变量
cwdstringstdio 传输可选子进程工作目录
headersobjecthttp 类传输可选自定义请求头
enabledboolean可选是否启用，影响启动时自动连接

传输协议适用场景 ​

传输协议适用场景优点注意事项
stdio本地 MCP Server 子进程简单、低延迟、适合本地工具需命令安全检查，敏感命令可能被拦截
SSE单向流式 HTTP 服务兼容现有 HTTP 基础设施SDK 升级计划中标记为 deprecated
streamableHttp现代 MCP Server官方推荐、支持更多特性需要服务端支持 Streamable HTTP
websocket双向实时通信低延迟、适合长连接非官方标准，兼容性需谨慎评估

连接参数调优建议 ​

  • stdio：优先使用白名单命令，避免高危命令；合理设置 env 传递敏感配置。
  • SSE/Streamable HTTP：通过 headers 注入认证头；注意 URL 必须有效。
  • WebSocket：仅在与服务端明确兼容时使用。
  • 连接重试：当前 MCP 客户端无内置重试，可在上层实现指数退避重试。

现象可能原因排查步骤

实际连接示例 ​

以下示例描述如何通过 Agent API 连接一个 stdio MCP Server：

  1. 添加 MCP Server：
    • 调用 POST /api/mcp/servers。
    • body 包含 id、name、transport=stdio、command、args、enabled=true。
  2. 连接 MCP Server：
    • 调用 POST /api/mcp/servers/connect。
    • body 包含 id。
  3. 获取工具列表：
    • 调用 GET /api/mcp/tools。
  4. 调用工具：
    • 调用 POST /api/mcp/call。
    • body 包含 serverId、toolName、args。

结论 ​

本实现以 McpClient 为核心，结合 registry.js 的多服务管理和 mcp-config.js 的配置持久化，提供了完整的 MCP 客户端能力。其特点包括：

  • 支持四种传输协议，适配不同 MCP Server 部署形态。
  • 工具自动发现流程清晰，连接成功后立即拉取工具列表。
  • 工具调用链路简洁，错误信息经过国际化处理。
  • 配置管理具备内存缓存和写入锁，提升安全性和性能。
  • 当前实现未内置连接池和重试机制，但可通过上层扩展实现。

未来可考虑的方向包括：

  • 增加连接超时和重试策略。
  • 支持 MCP SDK v2.x 的新特性，如 server/discover、Mcp-Method header 等。
  • 对 SSE 和 WebSocket 传输进行兼容性评估和迁移规划。
  • 增强工具参数校验和 schema 验证能力。
