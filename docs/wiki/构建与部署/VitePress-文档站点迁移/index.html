架构总览 ​

文档站点迁移的整体流程可以理解为：源文档 → 转换脚本 → 脚手架生成 → VitePress 站点 → 静态产物。其中，transform.mjs 是迁移过程中的关键中间层，它不关心文件系统 IO 和构建工具链，只负责把 Markdown 文本转换成 VitePress 友好的内容结构。

flowchart TD
SourceDocs["现有 Markdown 文档<br/>.qoder/repowiki/zh/content"] --> Transform["scripts/docsite/transform.mjs<br/>链接重写、Frontmatter、侧边栏"]
Transform --> Scaffold["scripts/docsite/scaffold.mjs<br/>站点脚手架生成"]
Scaffold --> VPConfig[".vitepress/config.mjs<br/>自动生成配置"]
VPConfig --> BuildScript["scripts/build-docsite.mjs<br/>调用 VitePress 构建"]
BuildScript --> ThemeSystem[".docsite/theme/<br/>主题系统集成"]
ThemeSystem --> Output["VitePress 静态站点<br/>docs/wiki/"]
Output --> Pagefind["Pagefind 搜索索引"]

图表来源

  • scripts/docsite/transform.mjs#L1-L164

  • scripts/build-docsite.mjs#L1-L69

该架构的关键约束包括：

  • transform.mjs 是纯函数模块，不应直接读写文件系统；IO 应由 build-docsite.mjs 或脚手架脚本承担。
  • 文档站点与扩展端构建相互独立：vite.config.js 面向 Chrome 扩展，build:docsite 面向 VitePress。
  • Agent 端通过 agent/package.json 独立发布，与文档站点无直接耦合。
  • 主题系统通过 .docsite/theme/ 目录提供完整的 Vue 组件和样式支持。

详细组件分析 ​

文档转换模块 scripts/docsite/transform.mjs ​

该模块是本次迁移中最具技术价值的部分。它提供了一系列导出函数，分别负责：

  • 将 file:// 源码链接转换为 GitHub blob 链接。
  • 将 <cite> 源码引用块包装为 VitePress 的可折叠区块。
  • 从 Markdown 首行标题和引言段落提取 Frontmatter。
  • 注入 VitePress 所需的 title 与 description。
  • 根据相对路径规划输出文件名与页面路由。
  • 重写 Markdown 内部相对链接，使其指向新的 VitePress 页面路径。
  • 构建文档目录树，并生成 VitePress 侧边栏结构。
  • 对组内"概览"标签进行兼容处理。
  • 新增 转义 HTML 标签和 Vue 插值语法，避免 VitePress 编译错误。
flowchart TD
Start["输入 Markdown 文本与相对路径"] --> WrapCite["wrapCiteBlock<br/>包裹源码引用块"]
WrapCite --> ConvertFileLinks["convertFileLinks<br/>file:// → GitHub blob"]
ConvertFileLinks --> RewriteMdLinks["rewriteMdLinks<br/>重写 .md 相对链接"]
RewriteMdLinks --> EscapeTags["escapeStrayTags<br/>转义 HTML 标签"]
EscapeTags --> EscapeMustaches["escapeMustaches<br/>转义  插值"]
EscapeMustaches --> ExtractFrontmatter["extractFrontmatter<br/>提取标题与描述"]
ExtractFrontmatter --> InjectFrontmatter["injectFrontmatter<br/>注入 frontmatter"]
InjectFrontmatter --> PlanPage["planPage<br/>计算 srcRel 与 pagePath"]
PlanPage --> Output["返回 { srcRel, content }"]

性能与构建特性 ​

从现有配置中可以观察到以下构建特性：

  1. 扩展端构建关闭 sourcemap
    vite.config.js 明确关闭 sourcemap，原因是扩展端产物会被打包进 Chrome 扩展包，开启 sourcemap 会导致体积膨胀并可能泄露源码。这与文档站点无关，但体现了项目对发布产物体积和安全性的重视。

  2. VitePress 作为开发依赖
    vitepress 位于 devDependencies，说明文档站点属于开发期产物，不应混入扩展端或 Agent 端的运行时依赖。

  3. 文档站点脚本独立于扩展端脚本
    build:docsite 与 build、build:silent 分离，避免文档构建干扰扩展端构建。

  4. 转换逻辑纯函数化
    transform.mjs 被设计为纯函数模块，便于单元测试、复用和调试，也符合"转换逻辑与 IO 解耦"的良好实践。

  5. 增强的安全检查
    构建脚本包含 6 项校验，确保文档站点的完整性和正确性。

  6. 主题系统集成
    通过 .docsite/theme/ 目录提供完整的 Vue 组件和样式支持，提升用户体验。

  7. 完整的测试覆盖
    单元测试覆盖了所有核心转换函数和主题集成逻辑，确保代码质量。

结论 ​

当前仓库已经完成了 VitePress 文档站点的完整实现：VitePress 依赖已引入，文档转换逻辑已增强，构建入口、脚手架、主题系统和样式均已实现。整个系统现在能够自动从 RepoWiki 源生成完整的 VitePress 文档站点，包含搜索功能、Mermaid 图表支持和完整的构建校验。

系统的核心优势包括：

  • 自动化程度高：从源文档到静态站点的完整自动化流程
  • 质量保证强：6 项构建校验确保文档站点的完整性和正确性
  • 功能丰富：集成搜索、图表渲染、响应式主题等现代文档站点功能
  • 可维护性好：清晰的模块化设计和纯函数转换逻辑
  • 扩展性强：基于 VitePress 生态，易于扩展和定制
  • 测试覆盖全面：完整的单元测试确保转换逻辑和主题集成的稳定性

在实施时，建议遵循以下原则：

  • 保持 transform.mjs 的纯函数性质，不直接操作文件系统。
  • 将构建脚本、脚手架、主题样式与文档内容解耦。
  • 文档站点与扩展端构建、Agent 端发布保持边界清晰。
  • 主题样式尽量对齐扩展端 CSS Token 体系，避免重复定义颜色。
  • 所有文档链接最终应指向可访问的 GitHub 源码或 VitePress 页面。
  • 充分利用现有的单元测试框架，为新功能添加相应的测试用例。
