引言 ​

本技术文档聚焦 RAG 文档处理管道，围绕多格式文档解析、动态路由加载、文本分块策略、预处理流程以及从上传到索引构建的完整链路展开。该管道位于 Agent 端的 RAG 子系统，负责将多种来源（本地文件、前端上传、URL）的文档统一解析为纯文本，再经分块、向量化后写入向量存储，同时保留原文备份以支持混合检索与重建。

项目结构 ​

RAG 文档处理相关代码集中在 agent/src/rag 下，其中文档解析与分块位于 document 子目录，知识库生命周期与导入编排位于 manager.js，配置与错误类型分别位于 config.js 与 errors.js。

核心组件 ​

  • 文档加载器（loader.js）：根据文件扩展名动态选择并懒加载对应解析器，返回统一文本与文件名。
  • 文本分块器（chunker.js）：段落优先断点 + 字符窗口兜底 + 重叠回退，输出带偏移区间的分块。
  • 解析器族（parsers/*）：
    • text.js：UTF-8 读取并去除 BOM。
    • pdf.js：通过 pdf-parse 提取 PDF 文本。
    • office.js：docx/xlsx/xls/pptx 等 Office 系列的多后端解析。
  • 配置（config.js）：集中维护扩展名路由表、默认分块参数、模型与批大小等常量。
  • 错误（errors.js）：定义 RagError 与错误翻译工具，便于上层响应层国际化。
  • 管理器（manager.js）：封装知识库生命周期、导入入口（文本/文件/URL）、分块、向量化、存储与备份、重建与恢复。

详细组件分析 ​

文档加载器与解析器路由 ​

  • 扩展名路由表由 config.js 的 PARSER_ROUTES 维护，loader.js 据此判断是否受支持并动态选择解析器名称。
  • 解析器采用按需 import，仅实际使用的格式才加载对应依赖，降低冷启动成本。
  • 不支持的扩展名会抛出 RagError('unsupportedFormat')，便于上层统一处理。

文本分块策略 ​

  • 自然断点优先级：优先在段落或句子边界切分，避免截断语义。
  • 字符窗口兜底：当找不到断点时，按 chunkSize 切分。
  • 重叠回退：下一块起点回退 overlap 字符，防止上下文断裂；同时保证 next > start 避免死循环。
  • 安全上限：超过 CHUNK_SIZE_WARN_LIMIT 会告警，避免被模型静默截断。

L -- 否 --> END["结束"]

解析器实现要点 ​

  • 文本类（text.js）：以 UTF-8 读取，去除首字节 BOM，避免影响 embedding 质量。
  • PDF（pdf.js）：通过 pdf-parse 提取文本；因 CJS 特性使用 createRequire 加载。
  • Office（office.js）：
    • docx → mammoth 提取纯文本。
    • xlsx/xls → xlsx 逐 sheet 转 CSV，保留行列结构。
    • pptx 及其他 → officeparser 通用解析。

文档预处理与元数据 ​

  • 编码处理：文本解析器显式处理 UTF-8 BOM；URL 链路通过 decodeBytes 按 contentType 解码（兼容 GBK 站点）。
  • 特殊字符清理：分块前对换行进行规范化，避免 \r\n 混用导致断点异常。
  • 表格数据提取：Excel 转为 CSV 文本，保留行列结构，利于检索理解。
  • 元数据保留：
    • 用户 metadata 先展开，系统键（documentName/source/createdAt）最后写入，确保不被覆盖。
    • 原文备份包含 id/name/text/source/metadata/chunkCount/createdAt，供 BM25 与重建使用。

端到端导入流程（文件/URL/文本） ​

  • 文件导入：
    • 本地路径：走沙箱校验（allowedPaths + 硬阻止清单），通过后交由 loader 解析。
    • base64 上传：体积预检后落临时文件，解析后删除。
  • URL 导入：
    • 安全抓取（重定向校验、私网拦截、响应体上限）。
    • HTML → htmlToText；PDF → 临时文件 + loader；其他 text/* → 解码为文本。
  • 统一入库：
    • 分块 → 批量向量化（含维度校验）→ 事务写入 VectraStore → 原文备份 → 更新注册表计数。

性能与容量控制 ​

  • 分块大小与重叠：默认 chunkSize=400、overlap=80，兼顾中文 token 上限与安全边界；超过 500 字符触发告警。
  • 批大小：EMBED_BATCH_SIZE=10，适配部分平台单次批量上限。
  • 导入体积限制：
    • 文本导入上限 10MB。
    • 文件上传上限 50MB（base64 长度近似换算）。
  • 内存保护：超大内容在解析/分块/向量化前快速失败，避免全量驻留内存。
  • 进度监控：导入各阶段（parsing/chunking/embedding/storing/done/error）均上报进度快照，供前端轮询。

故障排查指南 ​

  • 不支持的文件格式：
    • 现象：抛出 RagError('unsupportedFormat')。
    • 排查：确认扩展名是否在 PARSER_ROUTES 中；必要时添加新路由。
  • 内容为空：
    • 现象：emptyContent / emptyDocument / urlNoContent。
    • 排查：检查解析结果是否为空；URL 场景注意反爬壳页或无文本层 PDF。
  • 维度不匹配：
    • 现象：embeddingDimensionMismatch。
    • 排查：核对 embeddingConfig.dimensions 与实际模型输出维度是否一致。
  • 重建中断恢复：
    • 现象：进程重启后出现 .rebuild_* 目录或 rebuild_manifest.json。
    • 行为：自动收敛（完成换入/补提交/回滚旧索引/清理残留）。
  • 权限与密钥：
    • collections.json 落盘权限 0o600；apiKey 落盘前混淆，内存明文。

结论 ​

该 RAG 文档处理管道通过“扩展名路由 + 按需解析器 + 段落优先分块 + 批量向量化 + 原子重建”的组合，实现了多格式文档的统一接入与高可靠索引构建。其设计强调可观测性（进度上报）、安全性（沙箱/尺寸限制/权限）与可恢复性（重建清单与恢复逻辑），适合在生产环境中稳定运行。
