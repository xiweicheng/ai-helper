# 开源项目 i18n 国际化改造实战

AI Helper 最初完全是给自己用的，所以所有文案都是硬编码中文——UI 按钮、错误提示、工具描述、系统提示词，加起来 1500 到 2000 多处中文。后来项目开源到 GitHub，陆续有海外用户 star，我意识到一件事：**如果海外用户打开插件看到满屏中文，他们大概率会直接关掉。**

于是开始了 i18n 国际化改造。这篇文章记录一下整个过程和踩过的坑。

## 改造范围：六个阶段

i18n 改造不是加个翻译函数就完事的，涉及到项目的各个层面。我把它拆成了六个阶段：

**阶段一：基础设施搭建。** 新建 `src/shared/i18n.js` 模块，实现 `t(key, params)` 查表和参数插值功能。创建 `src/shared/locales/zh.js` 和 `en.js` 两个语言文件，按命名空间组织（common、dialog、settings、tool 等）。同时在设置页加语言切换 UI，manifest.json 加 `default_locale` 配置。拿 confirm-dialog 弹窗做了端到端试点，验证机制可行后再大规模推广。

**阶段二：UI 静态文案。** 侧边栏和选项页里所有硬编码中文——按钮文字、标签名、输入框 placeholder、提示语——全部替换成 `t()` 调用。这一步文案量大但逻辑简单，主要是体力活。

**阶段三：工具描述拆分。** 这是最关键也最 tricky 的一步。工具描述有两个消费方：给模型看的和给用户看的。给模型的描述统一用英文（大模型理解英文没有障碍，且固定英文能减少 token 消耗）；给用户在 UI 上看的描述走 i18n，按语言切换。原来硬编码中文的工具显示名（类似 `TOOL_DISPLAY_NAMES`）改为 i18n key 引用，运行时按当前语言查表返回。

**阶段四：报错、通知和 Toast 文案。** 这部分散落在各个工具执行逻辑里，包括工具执行失败返回给用户的错误消息、操作确认弹窗文案、各种状态提示。很多带参数插值，比如 `t('error.fileNotFound', { name: 'x.js' })`，需要逐个梳理。

**阶段五：划词工具栏文案。** 划词工具栏是 Content Script 注入页面的 UI，文案独立于侧边栏，需要单独处理。

**阶段六：系统提示词。** 注入给 LLM 的环境描述和规则，从中文改成英文。这部分用户看不到，但对模型行为有直接影响。

## 双轨 i18n 机制

改造中用到了两套 i18n 机制，各管各的：

- **manifest.json 的 name、description、commands**：用 Chrome 原生的 `chrome.i18n`，通过 `_locales/{en,zh}/messages.json` 和 `__MSG_xxx__` 占位符。这是 Chrome 扩展的强制要求。
- **JS 和 HTML 中的所有文案**：用自建的轻量 i18n 模块。`chrome.i18n` 的 `$1` 占位符不好用，同步 API 不支持运行时切换，所以自己写了一个。`t(key, params)` 支持点分嵌套 key、`{name}` 参数插值、运行时语言切换、订阅刷新，查找顺序是当前语言到英文 fallback 再到 key 本身。

自建模块还提供了 `registerTranslations(lang, dict)` 方法，各模块可以按需注册自己的文案，不需要全部堆在一个文件里。比如 IndexedDB 封装层、Offscreen Document 都各自注册了自己需要的 key。

## 哪些保留中文

i18n 改造有一条原则：**给模型看的用英文固定，给人看的按语言切换。** 但有些东西既不属于"给模型看的"也不属于"需要国际化的用户文案"，它们保留中文：

- **代码注释**：开发者看的，保持中文方便维护。
- **logger 日志**：调试用的运行时日志，保持中文，不影响用户。
- **executionLog 执行日志展示**：这是 ReAct 循环的执行追踪记录，偏向技术调试性质，保持中文。

这条原则帮我省了不少功夫。如果连 logger 日志都要 i18n，改造成本会翻倍，而且没有实际收益——没有人会在生产环境切换 logger 的语言。

## 经验教训

**第一，i18n 改造越早越好。** AI Helper 是在项目已经成型之后才做的 i18n，1500 多处硬编码文案要逐一排查替换，其中有大量散落在业务逻辑里的字符串，很容易遗漏。如果项目初期就建立 i18n 基础设施，后续新增功能时顺手用 `t()` 调用，成本会低得多。

**第二，要区分"给用户看的"和"给开发者看的"。** 前者必须 i18n，后者可以保持中文。听起来是废话，但实际操作中边界没那么清晰。比如工具执行失败时返回的消息，既会显示给用户看，也会被模型读取作为上下文。这种情况下，返回给用户的消息走 i18n，但模型看到的工具描述保持英文——双轨制解决了这个问题。

**第三，工具返回给模型的消息要 i18n。** 这一点容易被忽略。工具执行结果会作为 context 返回给模型，模型会参考这个语言来回复用户。如果工具返回中文错误消息，即使用户用英文提问，模型也可能用中文回复，体验很割裂。

## 最后

i18n 改造不是一个有技术深度的活，更多是耐心和细致。没有什么酷炫的架构设计，就是一点一点把硬编码替换成 key，然后确保两种语言下每个 key 都有对应的翻译。但做完之后，看到海外用户能用母语使用你的项目，那个感觉还是不错的。
