# 浏览器扩展架构选型：从 Manifest V3 到五层架构

开发一个有 44 个工具、多智能体、ReAct 推理循环的浏览器扩展，架构设计是最关键的一步。不是写代码难，是在各种限制下找到合理的结构难。

这篇文章聊聊 AI Helper 的架构是怎么一步步推演出来的。

## Manifest V3：绕不开的限制

Chrome 从 2024 年开始强制推行 Manifest V3，新开发的扩展没得选。MV3 带来的最大变化是 Service Worker 替代了 Background Page。

Background Page 是常驻的，有 DOM，有 window 对象，想干什么都行。Service Worker 不行——它没有 DOM，生命周期由 Chrome 管理，空闲一段时间会被直接终止，下次有事件再唤醒。这意味着你存在内存里的状态，可能一觉醒来就没了。

对 AI Helper 来说，这个问题尤其严重。ReAct 推理循环可能跑几十分钟，中间有大量的中间状态：当前迭代到第几轮、工具调用历史、Token 消耗统计、反思结果。如果 Service Worker 被终止，这些状态全丢，用户就得从头再来。

解决方案是 **chrome.storage.session + keepalive 端口**。session 存储在 SW 生命周期内有效，重启后还能读回来；keepalive 端口在 ReAct 循环运行期间保持连接，防止 SW 被回收。代码里用了一个 Map 来管理 keepalive 端口，以 sessionId 为 key，支持多会话并行。每次 ReAct 循环开始时建立端口，结束时断开，重连时也能正确恢复。

还有一个坑：剪贴板操作。MV3 的 Service Worker 没有 `navigator.clipboard` API，复制粘贴做不了。解决方案是 Offscreen Document——一个隐藏的页面，有 DOM 环境，可以执行剪贴板操作。Service Worker 通过消息通信把复制内容发给 Offscreen Document，由它来执行实际的 `navigator.clipboard.writeText`，还带了一个 `document.execCommand('copy')` 的后备方案。

## 五层架构

基于 MV3 的限制和功能需求，最终的设计是五层架构：

**第一层：Side Panel（UI 层）。** Chrome 114+ 提供的 Side Panel API，比 popup 空间大，比新开标签页体验好。所有用户交互在这里：对话、工具面板、会话管理、Token 统计、书签管理。80 多个状态字段的管理是个挑战，我用的是双导出 Proxy 模式——同时导出命名 `let` 绑定和 default 对象，default 对象通过 getter/setter 代理到同名 let 变量，确保两种导入方式共享同一份数据。没有用任何框架，纯 Vanilla JS。

**第二层：Background Service Worker（核心层）。** 这是整个扩展的大脑。ReAct 引擎、工具调度、反思系统、Token 预算管理、Agent 分发器都在这里。Service Worker 负责接收 Side Panel 的用户输入，选择合适的 Agent，注入 MCP 工具，预筛选工具列表，然后进入 ReAct 循环：模型推理 → 工具调用 → 结果反馈 → 反思 → 继续推理，直到任务完成或达到最大迭代次数。

**第三层：Content Script（页面工具层）。** 注入到用户浏览的网页中，负责实际的 DOM 操作：点击元素、填写表单、提取内容、滚动页面、截图。还有划词工具栏——用户选中文字时弹出的快捷操作栏。Content Script 的消息路由用 Map 实现了 O(1) 查找，避免 if-else 链条太长。

**第四层：Offscreen Document（辅助层）。** 前面提到的剪贴板兼容方案，纯辅助角色。

**第五层：Agent 服务（可选层）。** 一个 Node.js 服务，突破浏览器沙箱。连上之后，AI 可以读写本地文件、执行命令行、运行 MCP 服务器。这是可选的，默认不启用，需要用户主动安装和授权。Agent 端有自己的 Skill 系统和 MCP 注册表，可以动态扩展能力。

## 消息通信

五层之间的通信全靠 Chrome 扩展的 messaging API：

- Side Panel ↔ Background：`chrome.runtime.sendMessage` 和 `chrome.runtime.onMessage`
- Background ↔ Content Script：`chrome.tabs.sendMessage`，指定目标标签页
- Background ↔ Offscreen：也是 `chrome.runtime.sendMessage`，Offscreen 用 `chrome.runtime.onMessage` 接收

没有什么花哨的通信框架。Chrome 的 messaging API 够用了，关键是要设计好消息类型和响应格式，避免通信协议变成一团乱麻。

## 持久化策略

三种存储各司其职：

**IndexedDB** 用于存大块数据，7 个 object store：sessions（活跃会话）、activeSession（当前会话 ID）、archivedSessions（归档会话）、uiPrototypes（UI 原型）、tokenStats（Token 统计）、reactCheckpoints（ReAct 检查点）、bookmarks（消息收藏）。IndexedDB 的好处是容量大、支持索引查询，Side Panel 和 Service Worker 都能访问。

**chrome.storage.local** 用于存配置类数据：API 配置、Agent 定义、工具启用状态、语言偏好等。同步读写，API 简单，适合小量配置。

**chrome.storage.session** 用于跨 Service Worker 重启的状态恢复。ReAct 循环的检查点除了存 IndexedDB，还会在 chrome.storage.local 里存一份后备——当 IndexedDB 的 reactCheckpoints store 不可用时（比如版本升级冲突），用 storage 作 fallback。这个后备机制是踩坑后加的，之前出现过 SW 重启后 checkpoint 写入静默失败的问题。

## 数据流

完整的数据流是这样的：

用户在 Side Panel 输入指令 → Background 选择 Agent（决定用哪些工具和系统提示词）→ 注入 MCP 工具（如果配置了 MCP 服务器）→ 工具预筛选（根据上下文缩小工具范围，减少 token 消耗）→ 进入 ReAct 循环 → 每轮迭代先检查 Token 预算，超了就停止 → 调用 LLM → 解析模型输出的工具调用 → 路由到对应执行层（Content Script 做页面操作、Offscreen 做剪贴板、Agent 服务做本地操作）→ 收集工具结果 → 三级反思检查 → 继续下一轮或返回最终结果 → Side Panel 渲染输出。

## 在限制中找自由

回过头看，MV3 的限制反而逼出了更清晰的设计。

Service Worker 会随时终止？那就设计检查点和恢复机制，让任务可以从断点续接。没有 DOM？那就用 Offscreen Document 做隔离，核心逻辑不依赖 DOM。不能用 `eval`？那就用消息通信 + 事件驱动，反而让模块边界更清晰。

浏览器扩展的架构核心，我觉得就是这六个字：**在限制中找自由。** 不是和限制对抗，是接受限制、利用限制，让限制帮你做出更好的设计决策。
